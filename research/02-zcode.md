# ZCode (zai-org/ZCode) source research report — ARI protocol design research

> Repository: `ZCode/` (local clone, not checked into this repo; package.json version 3.14.0, Apache-2.0, TypeScript pnpm monorepo)
> Method: targeted source reading (grep + segmented reads). Every claim cites path + symbol; where not found, it says "not found in source".

## 1. Architecture overview

**What it is**: ZCode is an "AI coding workspace with three interfaces — desktop / browser / terminal"; the repository contains clients, backend services, shared UI, and the Agent CLI/runtime sources (README.en.md §"ZCode is an AI coding workspace"). The Agent CLI `zcode` also serves as the Agent runtime for Desktop and Web (README.en.md interface table, "Agent CLI ... which also provides the Agent runtime for Desktop and Web").

**Monorepo layout** (pnpm-workspace.yaml + architecture-policy.yaml modules):
- `apps/zcode-cli/` — an independent sub-monorepo (with its own pnpm-workspace.yaml/turbo.json) holding the Agent CLI and the runtime. Sub-packages: `core` (runtime core: agent/tool/runtime/session-context/compact/subagent/mcp/memory/hooks/permission, etc.), `bootstrap` (process bootstrap + zcode-protocol server + stdio transport), `cli`, `tui`, `contracts`, `shared-types`, `adapters`, `dynamic-workflow(-runtime)`, `node-repl-host`, `browser-use-plugin`, `superpowers-plugin`, `telemetry`, `i18n`, `debug` (listing of the apps/zcode-cli/packages/ directory).
- `packages/shared` — shared protocol and types (including `zcode-protocol-v4/` and the legacy `zcode-protocol/`); `packages/rpc` — RPC framework; `packages/client` — "Agent client SDK"; `packages/services` — business services (`zcode-agent/`, `session/`, `storage/`); `packages/server` + `packages/web` — web backend and frontend; `packages/ui` — shared React/Zustand; `packages/desktop` — Electron main/host/renderer (for the split see AGENTS.md §"Commands and repository structure" and architecture-policy.yaml `modules`).

**Layered flow (entry → runtime → tools → model provider)**: clients (desktop/web/tui) → `packages/services/src/zcode-agent/zcodeProtocolClient.ts` (protocol client) → `zcodeStdioTransport.ts` (stdio subprocess) → `apps/zcode-cli/packages/bootstrap` (zcode-protocol server: `transport.ts` / `server-operations.ts` / `v4-bridge.ts`) → `apps/zcode-cli/packages/core/src/runtime.ts` + `runtime/` (agent loop) → `core/src/tool/` (tools) → `core/src/model/` (model abstraction; model API access underneath is provided by `packages/provider` / `packages/provider-node`). The server (web backend) exposes the same runtime to the browser via `packages/zcode-server-cli`/the server package (README.en.md: during web development `@zcode/server` starts on :3030, with `/ws` and `/api` proxied to it).



## 2. Client protocol (ZCode Protocol V4)

Defined in: `packages/shared/src/zcode-protocol-v4/` (index.ts describes itself as a "data model draft (not frozen)" holding "only schema types + pure functions"). Coexists with the legacy `packages/shared/src/zcode-protocol/`. Version: `V4_WIRE_PROTOCOL_VERSION = 3` (core.ts; a comment notes that "projection snapshots keep using protocolVersion=1 independently").

**Transport and topology**: between client and runtime there are two faces — **RPC plus topic pub/sub**. The RPC side is JSON-RPC-style methods (`v4/command`, `v4/conversation/subscribe`, etc., see below); the event side is a stream of topic frames. There are three carrier tiers — embedded CLI/stdio (NDJSON), @zcode/rpc Channel socket (binary VQL header), mobile relay (base64 wrapping) — and `measureTopicNotificationEnvelopeBytes` measures each tier's real envelope separately (wire-codec.ts). Desktop launches the CLI subprocess over stdio (packages/services/src/zcode-agent/zcodeStdioTransport.ts); web goes through the server package proxying `/ws` (README.en.md).

**Handshake and capability negotiation**: host→client `HelloMessage {kind:"hello", protocolVersion, connectionId, clientMode: "desktop-continuous"|"web-remote-replayable", deliveryProfile: "continuous"|"replayable", serverTime, capabilities: HostCapabilities, auth}`; client→host `ClientHello {clientId, clientKind: "desktop"|"web"|"mobileRemote"|"mobileApp", appVersion, capabilities}` (transport.ts `helloMessageSchema`/`clientHelloSchema`). HostCapabilities = `{nativeDialogs, localTerminal, binaryFrames, compression: none|permessage-deflate, workspaceHookReview?, independentPlanState?}` (transport.ts `hostCapabilitiesSchema`) — optional fields checked with `=== true` for backward compatibility. deliveryProfile (core.ts `DELIVERY_PROFILES`): `continuous` (desktop, flushWindow 30ms, streaming text along the full path) vs `replayable` (web/mobile, 150ms window, no streaming, toolProgress only).

**Subscription model (event stream)**: `subscribeParamsSchema {topic: "conversation/<sessionId>" | "sessions-index/<workspaceId>" | "workspace-config/...", base: {logEpoch, seq}?, visibility: foreground|background}` → ack `{subscriptionId, mode: "snapshot"|"resume", logEpoch}` (transport.ts `subscribeParamsSchema`/`subscribeAckSchema`). If the client supplies a base watermark, deltas are replayed from that point; otherwise it receives a full snapshot — built on a **session event log keyed by logEpoch+seq**. Frame envelope: `{topic, subscriptionId, fromSeq, toSeq, sentAt, payload: {kind:"snapshot",snapshot} | {kind:"deltas",deltas[]}}` (transport.ts `createTopicFrameSchema`); the physical layer wraps it further in a `TopicWireFrame`: complete or fragment (when exceeding the 1MiB maxFrameBytes, UTF-8 byte fragmentation + crc32, fragmentIndex/Count/logicalBytes, deliveryKind: initial|online|recovery) (wire.ts `topicWireFrameSchema`/`topicFrameDeliveryKindSchema`).

**RPC method inventory** (grep `"v4/"` across the repo): control/query plane — `v4/command` (issue commands), `v4/commands/query` (pending command status), `v4/conversation/{subscribe,unsubscribe,resync,rowsRange,fileChanges,fileRewindPreview,backgroundBashOutput,usage,plans,workflowRuns,workflowRunEvents,workflowRunArtifacts,workflowRunArtifactRead,workflowRunArtifactData,workflowRunNodeResult,workflowRunWorkspace}`; attachments — `v4/attachment/{begin,chunk,commit,abort,read,previewSource}`; observability — `v4/telemetry/event`, `v4/usage/stats`, `v4/connection/flow`; controller plane — `v4/controller/{subscribe,unsubscribe,resync}`.

**Command dispatch (request/response)**: `commandEnvelopeSchema` + `commandPayloadSchemas` (command.ts) — commands are RPCs carrying idempotency keys (`commandKeySchema`; `COMMANDS_REQUIRING_BASE_REVISION` performs optimistic-concurrency baseRevision CAS; `ROW_TARGETING_COMMANDS` target by rowId+entityId); results are the `commandResultSchema` discriminated union (command.ts:367), plus `commandAckSchema`. Command table (command.ts `commandPayloadSchemas`): createSession, createSelectionSideSession, sendText, sendGoalCommand, stop, compact, forkAssistant, applyFileRewind, editUserQuery, retryTurn, setAssistantFeedback, sendQueuedNow/editQueueItem/reorderQueueItem/deleteQueueItem/setAutoDrain (input-queue management), resolveInteraction (**approval/question receipts**), snoozeInteractionAutoResolution, respondWorkspaceHookReview(+toggle/revoke/request), switchModelConfig, switchCollaborationMode, setFollowupMode, pauseGoal/resumeGoal, cancelBackgroundWork, resumeWorkflowRun, startSavedWorkflow, amendWorkflowRunSettings, renameSession, deleteSession, discardSharedContext. SubmissionMode = `["build","edit","plan","yolo"]` (submission.ts `submissionModeSchema`).

**Rate-limit/budget constants**: `PROTOCOL_V4_LIMITS` (core.ts) — maxFrameBytes 1MiB, logicalFrameAssembly 16MiB/1024 fragments, subscriberBuffer 500 ops/1MiB, eventRetentionPerSession 2000, snapshotTailWindowRows 60, rowsRangeMaxLimit 200, toolOutputFinalHead/TailBytes 32KiB, attachment 20MiB/512KiB chunk, etc.

## 3. Message model

V4 decouples the "client-visible projection" from "model API messages": the protocol carries only **Row + Delta + StatePatch** — no model messages.

**ConversationRow union** (rows.ts `conversationRowSchema`, discriminated on `kind`):
1. `turnHeaderRow` (turnHeaderRowSchema: includes turnWorkSegment) — turn boundary / work segment
2. `userInputRow` (userInputRowSchema) — user input
3. `assistantTextRow` (assistantTextRowSchema)
4. `reasoningRow` (reasoningRowSchema) — reasoning/thinking content row
5. `toolCallRow` (toolCallRowSchema) — fields: assistantResponseId?, toolCallId, toolName, `status: "inputStreaming"|"pendingApproval"|"running"|"success"|"error"|"cancelled"`, inputText, input, output: toolOutputSchema, display: toolCallDisplaySchema, error{code,message}, progress (replayable running state only), outputPreview, `approvalInteractionId` (points into pendingInteractions), `backgrounded`+`workId` (background handoff), startedAt/endedAt
6. `artifactRow` (artifactRowSchema) — artifact: artifactVersionId, logicalArtifactKey, artifactType(pdf|pptx|docx|xlsx|image|html|md|text), sha256, ref
7. `subagentRow` (subagentRowSchema) — subagent row
8. `hookInvocationRow` (hookInvocationRowSchema, + hookExecutionProjection) — hook execution projection
9. `timelineMarkerRow` (timelineMarkerRowSchema, timelineMarkerLane) — timeline marker

**ConversationDelta union** (delta.ts `conversationDeltaSchema`, discriminated on `op`, 5 ops in total): `row.appended` (append, the 99% case), `row.upserted` (whole-row replacement by rowId = state-machine transition), `row.removed {fromRowId}` (removes that row and everything after it = the edit/retry branches), `row.delta {rowId, path: "text"|"inputText"|"output.text"|"summaryText", append}` (streaming append, only for rows in a streaming state), `state.updated {patch}`. delta.ts header comment: "No row.inserted (mid-list insertion), no row.moved, no field-level JSON patch — for any structural change this model cannot express, the server always sends a snapshot resync, deliberately shrinking the client's error surface."

**StatePatch** (delta.ts `statePatchSchema`, whole-key replacement with a closed key set): revision, control, sharedContextImport, availability, inputRouting, meta, config, modelTransition, usage, queue, pendingInteractions, pendingCommands, backgroundWorks, subagents, workflowRuns, goal, plan, workspaceHookAdmission — each key's schema lives in snapshot.ts (e.g. pendingInteractionSchema, backgroundWorkSummarySchema, queueStateSchema, goalStateSchema, planStateSchema).

**Model API messages**: the protocol layer contains no Anthropic/OpenAI-style messages; model messages live inside the runtime (apps/zcode-cli/packages/core, see §5). Tool call rows are linked to the model response via `assistantResponseId` (rows.ts comment: "the text and the tools of the same model response share this ID"). The legacy protocol (packages/shared/src/zcode-protocol/) is still referenced by packages/ui (e.g. conversationProjectionStore.ts) and forms the old client surface.



## 4. Session

**Creation**: protocol command `createSession {workspaceId, firstInput{text,attachments,modelSelection,mode,planEnabled}, config, mcpServers, offPeakToolEnabled, dynamicWorkflowEnabled}` (command.ts); side session: `createSelectionSideSession` (a selection-side session). On the runtime side, `AgentRuntime` binds a `sessionId` at construction (agent-runtime.ts field `private sessionId: SessionId`), and the first event is `SessionCreated {planEnabled, mode, contextWindow}` (contracts session.events.ts `SessionCreatedPayload`).

**Persistence**: **SQLite**. Default path `~/.zcode/cli/db/db.sqlite` (packages/adapters/src/storage/session-store/paths.ts `getDefaultSessionDbPath`), overridable via `config.storage.sessionDbPath` (bootstrap/src/app/session-store.ts `getSessionDbPath`). The implementation `sqlite-session-store.ts` is built on `node:sqlite` `DatabaseSync` and implements `SessionStorePort` among other ports; the type imports reveal coverage of: sessions, messages (MessageInfo/MessagePart/MessageWithParts), input history (InputHistoryEntry), usage (TurnUsageRecord/ToolUsageRecord/ModelUsageRecord), todos, permission rulesets, script workflow definition/run/event/activity records, session task links, goal (SessionGoal), file diff (FileDiff), fork bundle (ForkCommitBundle/ForkChildSessionMetadata), shared-context import, etc. The message model is **message + parts** (session-transcript.ts `SessionTranscriptPart = {text|thought|tool{toolCallId,toolName,input,output,status,title,resultDisplay}}`, role: user|agent).

**Dual-track event sourcing**: the runtime's in-memory `InMemorySessionEventStore` (contracts events/in-memory-session-event-store.ts) holds `SessionEvent{id, sessionId, turnId, type, timestamp, traceId, sequenceNumber, payload}`; persistence is primarily the message store. The V4 projection synthesizes events back from the transcript: bootstrap/src/zcode-protocol-v4/transcript-hydration.ts — its comment states "reduce(transcript) ≡ reduce(events)"; fork child sessions / rewind truncation touch only the message store, and cold-subscribe hydration synthesizes a SessionEvent sequence back out of the transcript and then reduces it, guaranteeing that historically visible running states do not disappear after a restart.

**Resume**: `resume.ts` (runtime/methods, 453 lines) + `ResumeSessionOptions/ResumeSessionResult` (runtime/types.ts); `SessionResumedPayload {directory, interruptedToolCount, messageCount, partCount, recoveredCompactTimelineCount, recoveredSteerInputCount, resumedTodoCount}` — **crash recovery** covers the interrupted-tool count, the steer-input count, and recovery of the compact timeline. CLI-side resume event `Resume`, plus the set of persisted-cancellation error codes `PERSISTED_CANCELLATION_CODES` (transcript-hydration.ts).

**Fork/Rewind**: `session-fork.ts` (1487 lines, runtime/methods) + `WorkspaceForkResult`; protocol commands `forkAssistant {target: conversationRowTarget}`, `applyFileRewind {target}`, `editUserQuery {target, newText, workspaceMode: preserve|rewind}`, `retryTurn {target}` (command.ts); query `v4/conversation/fileRewindPreview`. File level: `file-rewind.ts`, `rewind.ts`, `workspace-checkpoints.ts` (`WorkspaceCheckpointSummary`, `WorkspaceRewindRestoredFile`, checkpoint events `CheckpointCreated`, `RewindTriggered`, `application/vnd.zcode.workspace-checkpoint+json`).

**Multi-client**: one CLI process + a multi-subscriber model — the subscribe `subscriptionId` together with deliveryKind=recovery supports multiple consumers each with their own watermark; `clientKind: desktop|web|mobileRemote|mobileApp` (transport.ts). **Interrupt/Cancel**: protocol command `stop {expectedForegroundExecutionId?}`; events `Interrupt`, `Cancel`, `TurnError`; `StopActiveForegroundExecutionOptions/Result` (runtime/types.ts).

## 5. Agent loop

Core files: runtime/methods/turn-loop.ts `runRegularTurnLoop` (while(true), each iteration = one model step) + turn.ts (turn entry, 872 lines) + turn-machine.ts (state-machine abstraction) + turn-model-step.ts (provider call) + turn-step-finish.ts.

**Single-turn control flow** (turn-loop.ts): ① `throwIfTurnAborted(turnAbortSignal)`; ② drain pending runtime commands (steering inputs, background subagent results, and workflow results merge into turnRequestState); ③ `microcompactIfNeeded` (phase: PreRequest|MidTurn); ④ `evaluateRapidRefill` + `autoCompactIfNeeded(CompactReason.ContextLimit)`; if consecutive rapid refills exceed the limit, throw `createCompactRapidRefillError` (circuit breaker); ⑤ `initializeMcp` + `getTools` (filtered by `toolDisallowlist`/automation/off-peak restrictions; scheduled-task turns forbid writing task definitions to prevent recursion); ⑥ inject system reminders: `plan_mode_exit`/`runtime_mode`/`todo_reminder`/`output_style` (provider-visible attachments; output_style is not persisted to the session); ⑦ `buildRuntimeProviderRequestMessages` (provider-visible ordered projection + cache-control anchors set uniformly after projection); ⑧ `TurnMachineImpl.startModelRequest` → `runModelBackedTurnStep`; a `"break"` result exits the loop.

**TurnMachine state machine** (agent/turn-machine.ts `TurnMachine`): start → startModelRequest → (addStreamingContent|receiveModelResponse) → scheduleTools → startToolExecution → completeTool → aggregateResults → complete/fail; plus requestPermission/resolvePermission and queuePendingInput/drainPendingInputs. `TurnPhase` is derived via `getNextPhase()`.

**Context budget / iteration**: model steps have no hardcoded max-iterations (no fixed iteration cap found in source; termination relies on the turnControl/stopTurnOnSuccess tools, the stop command, and errors); `turnOutputTokenContinuation` (continues after output-token truncation, filterOutputTokenContinuationEntries), `target-continuation-loop.ts`, `streaming-recovery.ts` (stream-interruption recovery). **Retry/loop detection**: `repeatedToolCallSignature`/`repeatedToolCallStreakCount` (referenced in turn-loop.ts, defined in turn-loop-state.ts) — a streak counter for tool calls with the same signature. **parallel**: ToolScheduler parallel groups (see §6); **steering**: `TurnSteerQueued/Drained/...` events + `steering.ts` — guide mode injects in one shot vs queue mode enqueueing.

## 7. Approval / Permission

**Two-gate model**: rule evaluation (PermissionService, synchronous) + a client-side broker (asynchronous human confirmation).
- `PermissionService.checkPermission(context, toolCapability, projectRules, rulePolicy) → PermissionDecisionResult` (core/permission/service.ts). `PermissionContext {toolName, input, riskLevel, mode, planEnabled, prePlanMode, workingDirectory}`; `PermissionBehavior = "allow"|"ask"|"deny"`; the result carries `modifiedInput` (**the permission layer may rewrite tool arguments**), `escalated`, `ruleId`, `alwaysAsk` (a structured marker saying "this ask originates from the tool's alwaysAsk declaration; a PreToolUse hook cannot erase it").
- Tool capability declaration `PermissionToolCapability {allowedInPlanMode, alwaysAsk, readOnly, destructive, requiresUserInteraction, sideEffectScope, riskLevel, needsApproval, permissionCapabilityGroup, permission: ToolPermissionSpec}` (service.ts).
- Rule persistence: `PermissionRuleset {version:1}` + `applyPermissionUpdates(ruleset, PermissionUpdate[])`; `PermissionUpdate = {type:"addRules", behavior, rules: PermissionRuleValue[]}` (contracts interfaces/permission.port.ts). Session-scoped "Always allow in this session" = `grantSessionPermission`, kept only in runtime memory and dying with the session (service.ts comment). Plan-mode transitions have a dedicated `resolvePlanModeTransitionPermission` (plan-mode-policy.ts).

**Waiting for client confirmation (broker)**: `PermissionBrokerPort` / `ManualPermissionBroker` (core/permission/broker.ts) — a pending map deduplicated by requestId (duplicate requests throw `InvalidStateTransition`), with timeouts; without a broker, `DenyPermissionBroker` falls back to deny. Request structure `PermissionBrokerRequest {requestId, sessionId, turnId, traceId, toolCallId, toolName, ...}` (contracts permission.port.ts). Events: `PermissionRequested` → `PermissionResolved|PermissionDenied`.

**Client-visible form (V4 projection)**: pending interactions hang off the StatePatch's `pendingInteractions[]` (snapshot.ts `pendingInteractionSchema`): `{interactionId, kind: "permission"|"userInput"|"workspaceHookReview", anchorRowId(nullable, null=session-level), createdAt, autoResolution, payload}`. **Permission payload**: `{toolCallId, toolName, summary, detail, freeText?, origin?, display(the tool's self-reported confirmation preview, reusing toolCallDisplay), fullAccessOption?(PERMISSION_FULL_ACCESS_OPTION_ID="fullAccess"), options: [{optionId, label, kind: "allowOnce"|"allowAlways"|"deny"|"custom", response}]}` (snapshot.ts `permissionRequestPayloadSchema`/`permissionOptionSchema`). In parallel, toolCallRow.status = "pendingApproval" and `approvalInteractionId` points back to the interaction — **how the client knows it is waiting: StatePatch.pendingInteractions non-empty + the tool call row's status**. Receipt: protocol command `resolveInteraction {interactionId, answer{optionId?, freeText?, action: accept|decline|cancel?, content?}}` (command.ts). **Argument editing**: `PermissionDecisionResult.modifiedInput` (rewritten on the runtime side); client-side freeText feedback and AskUserQuestion multi-question answers (`userInputRequestPayloadSchema {prompt, freeText, options, sensitive, questions[], schema}`). The first action on an AskUserQuestion permanently suspends auto-resolution: `snoozeInteractionAutoResolution` (command.ts). Also permission-options.ts / permission-suggestions.ts / permission-rules-persistence.ts (executor/ directory; suggested rules and persistence to disk).

## 8. File / Diff

**Protocol surface**: dedicated RPCs `v4/conversation/fileChanges` and `v4/conversation/fileRewindPreview` (grep "v4/" hits; server-side implementation in the bootstrap v4-bridge); the file rewind command `applyFileRewind`. **Diff data type**: `FileDiff {path, additions, deletions, oldPath?, newPath?}` (contracts interfaces/session-store.port.ts — renames are expressed via old/newPath; no hunk-level content). The tool-result display layer has `FileDiffToolResultDisplayPayload` (contracts tools/tool-result-metadata.ts). tool/diff.ts provides diff computation for the edit tool.

**Change-representation philosophy**: file modifications are not an independent event stream but **toolCallRows (Edit/Write tool rows) + a turn-level summary**. contracts has `TurnFileChangeSummary` (imported by transcript-hydration.ts) — file changes summarized per turn; toolCallRow.status/output/display carry the results. The V4 event log has no standalone file.changed event (not found in source; file changes are projected through tool results and the turn summary).

**Snapshot/rollback**: workspace checkpoints — `workspace-checkpoints.ts` + `WorkspaceCheckpointSummary`/`WorkspaceFileRewindApplyResult`/`WorkspaceRewindRestoredFile` (runtime/types.ts), events `CheckpointCreated`/`RewindTriggered`, MIME `application/vnd.zcode.workspace-checkpoint+json` (grep hits in bootstrap); `SessionRevert {messageID, partID?, snapshot?, diff?}` (session-store.port.ts) ties session rollback to file snapshots. The SQLite side has FileDiff/ForkCommitBundle storage columns.

## 10. Context management

**Context construction**: `ContextBuilder.build() → ContextBuildResult {sections: ContextSection[]}` (core/context/builder.ts) — a structured list of sections, each carrying `chars/tokens(estimateTokens)/injectionTarget("system"|...)/cacheHint("dynamic"|"stable")`; section 1 = the CLI prefix "You are ZCode, an interactive coding agent", section 2 = the stable persona or customSystemPrompt, with the special identity workflowActor (mutually exclusive with customSystemPrompt; an error is thrown if both are present); `addSection` supports extension; tool descriptions are no longer mirrored into the system prompt (carried by the request's tools field, builder.ts comment). `context/dynamic-sections.ts` + `context/sections/`. Subagents get a separate `SubagentContextBuilder extends ContextBuilder` (subagent/context-builder.ts).

**Compaction (two levels)**:
- **auto-compact**: `autoCompactIfNeeded` (runtime/methods/compact.ts, from line 184) — decided by `shouldAutoCompact({messages, config, consecutiveFailures, tokenOverride})` (thresholdTokens is derived by `getAutoCompactThreshold`/modelContextBudgetStrategy/contextWindow+maxOutputTokens, compact.ts:267); trigger reasons `CompactReason.ContextLimit|UserRequested|ProviderOverflow` (compact.ts:92,425 — after the provider reports context exceeded, `reactiveCompactAfterContextExceeded`); summary model request `compact-summary-model-request.ts`; rapid-refill circuit breaker (`MAX_CONSECUTIVE_RAPID_REFILLS`, `RAPID_REFILL_TOOL_TURN_THRESHOLD`, turn-loop-state.ts).
- **microcompact**: `microcompactIfNeeded` (two phases, PreRequest|MidTurn, invoked every turn by the turn loop) — `LocalMicrocompactPolicyConfig.thresholdTokens ?? buildDefaultMicrocompactThreshold` (microcompact.ts:112).
- **Visibility**: events `CompactStarted/Completed/Failed/CompactBoundary/MicrocompactBoundary`; payload `SessionCompactedPayload {compactBoundary, summary, preservedEventCount, removedEventCount}` (session.events.ts); recovery count `recoveredCompactTimelineCount` (SessionResumedPayload). **Snapshot/restore**: compact timeline persistence in `compact-persistence.ts`.

**Transcript**: the message store (SQLite) is authoritative; projection skips summary messages and model-only user messages (session-transcript.ts comment: "runtime-internal inputs such as goal continuation stay in the raw history for the model to recover, but the transcript is the user-visible projection"). `read-session-context.ts` provides the ReadSessionContext tool (reads transcripts across sessions, "Cleaned transcript" title, :70).

**Tool output truncation**: `PROTOCOL_V4_LIMITS.toolOutputFinalHeadBytes/TailBytes = 32KiB` (head+tail truncation on the protocol surface); `ToolMetadata.maxOutputBytes` (tool metadata layer); usage-observability.ts records the `truncated` flag. Streaming profile streamOutputCapBytes (continuous 256KiB, replayable 0 = no streaming), core.ts DELIVERY_PROFILES. **Others**: `context-history-entries.ts`, `residency.ts` (residency policy), project memory (core/src/memory/, memory-file-path.ts), `context-refresh.ts`.

## 11. Subagents

**Supported and deeply integrated**. Tool: `Agent` (tool/handlers/agent.ts; the legacy names Task/subagent also appear in hydration's `SUBAGENT_TOOL_NAMES`) + a dedicated Explore subagent (subagent/explore.ts, createExploreSubagentPort).

**Lifecycle** (subagent/runner.ts, ~915 lines): the `SubagentPort` interface includes `SubagentLaunchRequest/RunRequest/StartRequest`, `SubagentSendMessageRequest`, `SubagentStopOptions`, `SubagentWaitOptions`, `SubagentTaskSnapshot`, `AgentBackgroundedOutput`; **each subagent gets its own sessionId** (`createSessionId()` called in the runner) + a child trace context; profile-driven: `AgentProfile` (subagent/profile.ts, frontmatter parsing in profile-frontmatter.ts, per-profile optional modelSelection + a getAllowedTools allowlist); dual foreground/background lifecycle (`runInBackground === true || profile.background === true`); completion notifies the parent session via `ParentTaskNotificationCommand`/completion-notification.ts; `runtime-task-registry.ts` tracks active child tasks.

**Protocol visibility**: `subagentRow {parentToolCallId, subagentType, status: running|success|failed|cancelled, summaryText, childSessionId?, backgrounded?, workId?}` (rows.ts) — **when childSessionId is present, the UI can drill down by subscribing to conversation/<childSessionId>** (the rows.ts comment states explicitly that child rows are not embedded). **Event forwarding**: subagent/tool-event-mirror.ts mirrors the subagent's ToolCall{Scheduled,Started,Progress,Result,Error} and Permission{Requested,Resolved,Denied} events into the parent session's event stream, with toolCallId prefix `tool_subagent` and source="subagent". StatePatch has a `subagents` key (subagentProjectionStateSchema). **Parallelism**: spawning multiple subagents and background running are both supported; steering: subagent/message-steering.ts.

## 12. PTC (Programmatic Tool Calling)

ZCode has no Anthropic-style "tool-use code API", but it has two channels for "the model writing code to invoke capabilities":

1. **NodeRepl (the js tool)**: tool/handlers/node-repl.ts — "one persistent NodeReplSession per zcode session, retaining in-memory state (globalThis) across js calls, key = context.sessionId" (node-repl.ts comment); contracts JsInputJsonSchema/JsOutputSchema (@zcode/contracts); host process packages/node-repl-host; inside the REPL, `agent.browsers` is accessible (browserControlPort is passed through when the browser-use plugin is enabled, setupBrowserRuntime). The model composes capabilities programmatically inside a persistent JS sandbox — this is ZCode's mechanism closest to PTC. tool-input-validation-model-content.ts handles model-content validation for the REPL.

2. **Dynamic Workflow (dwf)**: the model submits a script via the `CreateWorkflow` tool → `validateCreateWorkflowSource`/`resolveCreateWorkflowInput` (create-workflow-source.ts) **statically typechecks it against the facade first** (the dynamic-workflow package: compiler/engine/facade/lowering/schema/analysis, including the phase-marker diagnostics `collectPhaseMarkerDiagnostics`) → the user confirms at the gate (`prepareApproval` drops the prompt when compilation fails, create-workflow.ts comment) → `DynamicWorkflowRunPort.submit` starts the run in the background (output `{status:"backgrounded", backgroundTaskId: runId}`) → the engine executes it in dynamic-workflow-runtime (harness.ts, child process child-entry-file.ts/child-source.ts) → progress is appended to the **parent session** as the `DynamicWorkflowRunProgress` event ("the run itself has no session", session.events.ts comment) → projected into the StatePatch `workflowRuns` key (workflowRunsStateSchema, workflow-runs-reducer.ts, 641 lines). The protocol surface has a full query/control set: `v4/conversation/workflowRuns/workflowRunEvents/workflowRunArtifacts/workflowRunArtifactData/workflowRunNodeResult/workflowRunWorkspace/workflowRunArtifactRead` + commands `resumeWorkflowRun`/`cancelBackgroundWork`/`startSavedWorkflow`/`amendWorkflowRunSettings`/`saveWorkflow`/`amendWorkflow*`/`getWorkflowRun*`/`listWorkflowRuns`/`evalWorkflowSnippet`. The script's `artifact.*` publications and its top-level return value are two separate things (workflow-artifacts.ts file header comment).

**Intermediate events**: a dwf run's node progress (workflow-runs-node-progress.ts, phases/concurrency/lineage modules) streams into the parent session in real time; NodeRepl has no intermediate events (a single tool call). tools.ts (runtime/methods) registers the two tool families into the provider-visible contract (ordering in tool/provider-visible-order.ts).

## 14. What the Shell must see vs. runtime internals

1. **The protocol exposes only the projection (Row/Delta/StatePatch), not model messages**. Model API messages, provider request structures, and cache-control anchors are all runtime internals (buildRuntimeProviderRequestMessages, turn-loop.ts); a Shell built from scratch only needs to implement the Row projection + the 5 delta ops.
2. **The event log watermark (logEpoch+seq) is the core of the resume protocol**. The Shell must persist each topic's last seq to be able to resume after a reconnect; the snapshot is a fallback, not the norm (subscribeParamsSchema.base, transport.ts).
3. **deliveryProfile is a product-tier contract**: desktop = continuous (streaming text + 30ms flush); web/mobile = replayable (no streaming, relying on the progress field + replay). The Shell must pick the tier matching its own form and report clientMode honestly.
4. **Capability negotiation evolves additively via optional booleans**: HostCapabilities/ClientHello check for absence with `=== true` (workspaceHookReview, etc.); a Shell implementing new capability fields must tolerate old ends ignoring them.
5. **Approval is data, not a callback**: pendingInteractions is an ordinary state key in the StatePatch, and the receipt goes through the `resolveInteraction` command; the Shell does not need to implement an RPC callback channel — it renders state + sends commands.
6. **The three permission tiers (allow/ask/deny) + the four option kinds (allowOnce/allowAlways/deny/custom) are adjudicated by the runtime**; the Shell only displays the options and freeText; `modifiedInput` (argument rewriting) happens in the runtime — the Shell does not need to understand the rule engine.
7. **toolCallId is the end-to-end correlation key**: subagent mirrored events carry the prefix `tool_subagent`, approval interactions anchor via approvalInteractionId, background tasks carry workId — when building aggregate UI, the Shell relies on these ids for correlation rather than guessing from temporal ordering.
8. **Tool-parallelism semantics are guaranteed by the runtime**: the Shell does not need to understand parallelGroups/topological sorting and can simply render in row.upserted order; but if the Shell builds its own scheduler, it must implement the four-way readOnly/destructive/concurrentSafe/sideEffectScope determination + cycle detection.
9. **Background-task output is pull-based**: while running, a bounded outputPreview is pushed; the full output is pulled via `v4/conversation/backgroundBashOutput` (8KiB cap + outputPath on-disk truncation flag) — the Shell must implement this push/pull pair and cannot assume the full output will be pushed.
10. **File changes are a projection of tool results, not standalone events**: to display diffs, the Shell must combine toolCallRows (Edit/Write) + TurnFileChangeSummary + `v4/conversation/fileChanges`; hunk-level patches do not enter the protocol — the UI must recompute them from workspace files itself or pull a preview.
11. **Rollback has two layers**: the session layer (editUserQuery/retryTurn/forkAssistant targeting by conversationRowTarget) and the file layer (applyFileRewind + checkpoints) — the Shell's undo UX should distinguish these two layers rather than offering a single undo.
12. **Compaction is nearly transparent to the client but leaves traces**: the CompactBoundary/MicrocompactBoundary events + row-level summary/removedEventCount; the Shell needs to render a "compacted" boundary bar, but cannot assume historical rows disappear (the projection keeps the timeline).
13. **The right client-side form for a subagent is "row + on-demand subscription"**: subagentRow carries only summaryText/childSessionId, and the child conversation is reached by drilling down via a subscription to conversation/<childSessionId> — the Shell should not expect the parent session stream to embed all subagent output.
14. **Timeouts/budgets are the runtime's responsibility but the Shell must be aware of them**: ToolDeadline is pausable (admission queuing does not count), the rapid-refill circuit breaker throws, output token continuation keeps going — the Shell will see non-linear sequences like "tool failure → automatic retry/continuation" and cannot assume "one call = one result".
15. **Multi-client concurrency is a first-class design constraint**: subscriberBuffer limits (500 ops/1MiB), deliveryKind=recovery, idempotencyTablePerSession=512, pendingCommandsDisplayMax — the Shell must treat "another client may be issuing commands / consuming events concurrently" as the normal case.
