# 07 · Codex App Server source-level survey (openai/codex, crate: codex-rs/app-server)

> Subjects of study: `codex-rs/app-server` (JSON-RPC server) + `codex-rs/app-server-protocol` (protocol definitions).
> Local repo: `codex/` (not committed to this repository). All conclusions cite source path + symbol evidence.

## 1. Transport & framing (JSON-RPC over stdio?)

**Line-delimited JSON, not Content-Length (LSP style).** Across the repository (app-server / app-server-transport), `Content-Length` appears only in remote_control's HTTP/WebSocket handshake tests; stdio is read line by line with `std::io::stdin().lock().lines()` and written out with `json.push('\n')` (`codex-rs/app-server-transport/src/transport/stdio.rs:73,141`). The stdio connection includes EOF cleanup and SIGTERM handling ("SIGTERM received; closing stdio connection (45s shutdown deadline)", stdio.rs:158).

**Multiple transport backends**: `ConnectionOrigin` distinguishes connection origins; `app-server/src/transport.rs` re-exports `start_stdio_connection` / `start_websocket_acceptor` / `start_control_socket_acceptor` (Unix socket) / `start_remote_control` (remote-control WebSocket, with pairing, auth, and daemon mode) (transport.rs:25-44). That is, three classes: stdio (local IDE), Unix control socket, WebSocket (local acceptor + remote control).

**Bidirectional requests: supported.** server→client JSON-RPC requests are enumerated by `server_request_definitions!` (`codex-rs/app-server-protocol/src/protocol/common.rs:1761`): `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/tool/requestUserInput`, `mcpServer/elicitation/request`, `item/permissions/requestApproval`, `item/tool/call` (DynamicToolCall, client tool-call callback), `account/chatgptAuthTokens/refresh`, `attestation/generate`, `currentTime/read`. The send side uniformly goes through `outgoing.send_request(ServerRequestPayload::…)`, which returns `(pending_request_id, rx)` and then `tokio::spawn`s to await the response (`codex-rs/app-server/src/bespoke_event_handling.rs:804-814`); the outbound envelope is `OutgoingEnvelope::{Broadcast, ToConnection}` (`app-server/src/outgoing_message.rs:117,407-455`), i.e. a single server process can serve multiple connections.

**Handshake**: client→server `initialize`, params `InitializeParams{client_info: ClientInfo{name,title,version}, capabilities: InitializeCapabilities}` (v1.rs:44-75); capabilities include `experimental_api` (opt-in experimental methods/fields), `request_attestation`, `opt_out_notification_methods` (suppress notifications by method name, e.g. `thread/started`), `extensions` (MCP extensions). The connection state `ConnectionState.outbound_initialized / outbound_experimental_api_enabled` (app-server/src/transport.rs:37-45) gates outbound traffic accordingly.

All client→server methods are defined by the macro `client_request_definitions!` in `common.rs:498-1490` (variant => wire method). This checkout uses **v2 thread.* naming**; the old names assumed in the task brief such as `newConversation/sendUserMessage/addUserVoiceMessage` were **not found in the source** (repo-wide grep, no hits). ## 3. Approvals (execCommandApproval / applyPatchApproval)

**Exec approval flow**: core emits `EventMsg::ExecApprovalRequest` → app-server assembles `CommandExecutionRequestApprovalParams` (v2/item.rs:1544): `kind` (command|writeStdin, `CommandExecutionApprovalKind` item.rs:79), `thread_id/turn_id/item_id`, `started_at_ms` (approval UI timing), `approval_id` (routing UUID for zsh-exec-bridge sub-commands / when multiple callbacks belong to one itemId), `environment_id`, `reason`, `network_approval_context`, `command`, `cwd`, `command_actions` (parsed actions, for display), `additional_permissions`, `proposed_execpolicy_amendment`, `proposed_network_policy_amendments`, `available_decisions` (server-declared list of selectable decisions, experimental feature). It is sent to the client via `outgoing.send_request(ServerRequestPayload::CommandExecutionRequestApproval(params))`, and the `(pending_request_id, rx)` is handed to `on_command_execution_request_approval_response` to await asynchronously (bespoke_event_handling.rs:785-814). The client replies with `CommandExecutionRequestApprovalResponse{decision}` (item.rs:1618).

**Decision enum** `CommandExecutionApprovalDecision` (item.rs:66): `Accept`; `AcceptForSession` (writes to a session-level approval cache so later commands of the same kind skip the prompt); `AcceptWithExecpolicyAmendment{execpolicy_amendment}` (persists an execpolicy rule); `ApplyNetworkPolicyAmendment{network_policy_amendment}` (per-host allow/deny rules); `Decline` (refuse but the turn continues); `Cancel` (refuse and immediately interrupt the turn). Mapped via `From<CoreReviewDecision>` (item.rs:87-110; `TimedOut→Decline`).

**Can the client modify the command? No.** The response carries only `{decision}`; no "modified command" field was found in the source. The closest thing to "modification" is attaching an execpolicy/network policy amendment on approval (changing rules, not the command).

**FileChange approval**: `item/fileChange/requestApproval`, `FileChangeRequestApprovalParams{thread_id,turn_id,item_id,started_at_ms,reason,grant_root}` (grant_root is an UNSTABLE "allow writing to this root for this session" request, item.rs:1624-1645); response decisions `FileChangeApprovalDecision{Accept, AcceptForSession, Decline, Cancel}` (item.rs:115-127). Also present: `item/permissions/requestApproval`, `mcpServer/elicitation/request`, `item/tool/requestUserInput` (multiple-choice user input).

**Policy configuration (per thread + per-turn overrides)**: `ThreadStartParams.approval_policy: Option<AskForApproval>`, `sandbox: Option<SandboxMode>`, `approvals_reviewer: Option<ApprovalsReviewer>` (v2/thread.rs:69-75); `TurnStartParams.approval_policy/sandbox_policy/permissions/approvals_reviewer` can be overridden per turn and take effect for subsequent turns (v2/turn.rs:207-226). `AskForApproval`: `untrusted` / `on-request` (default, alias `on-failure`) / fine-grained variants (protocol.rs:969-981); `SandboxMode`: `read-only` (default) / `workspace-write` / `danger-full-access` (config_types.rs:104-112). `approvals_reviewer` can be set to `auto_review` (legacy alias `guardian_subagent`) — **the server internally uses a subagent to make the risk decision and then approve/reject**, i.e. the approver need not be the client (v2/shared.rs:237-261).

## 4. Threads vs Conversations (naming/versioning, fork, dynamic tools)

**Naming and versioning**: the current API uses `thread.*` throughout; the old `conversation.*` / `newConversation` / `sendUserTurn` naming was not found in this checkout's source (only namespace-less top-level legacy methods such as `getConversationSummary`, `getAuthStatus`, `gitDiffToRemote`, `fuzzyFileSearch` remain at the tail of client_request_definitions, common.rs:1330-1490). Versioning is not two parallel v1/v2 method tables: `protocol/v1.rs` (247 lines) carries only `initialize` and shared types, while `v2/` carries all modern methods; the experimental surface is annotated with the `#[experimental("thread/start.dynamicTools")]` attribute and gated by negotiation via `InitializeCapabilities.experimental_api`, with outbound fields additionally stripped by hand through `strip_experimental_fields()` (item.rs:1605). `ClientRequestSerializationScope` (common.rs:129-160) does keyed serialization by Global/Thread scope, supporting multiple threads concurrent on one server.

**fork**: `thread/fork` (common.rs). resume: `thread/resume` supports an id or a rollout file `path` (experimental `thread/resume.path`, thread.rs:368); full-history injection is deprecated in favor of `thread/resume.initialTurnsPage` + `thread/turns/list` + `thread/items/list` pagination (thread.rs:421-428); there is also `thread/revert`.

**Dynamic tools / client tool inversion: supported, and running over the same JSON-RPC channel as approvals.** Declaration: `ThreadStartParams.dynamic_tools: Option<Vec<DynamicToolSpec>>` (thread.rs:145-150, with accompanying `DynamicToolNamespaceSpec/DynamicToolNamespaceTool` namespaces, thread.rs:30-31). Invocation: the runtime produces `CoreTurnItem::DynamicToolCall` → app-server emits an `item/started` notification + **server→client request `item/tool/call`** (`DynamicToolCallParams{thread_id,turn_id,call_id,namespace,tool,arguments}`) → `crate::dynamic_tools::on_call_response(call_id, rx, conversation)` feeds the client's result back into core (bespoke_event_handling.rs:1086-1115,973-974).

**viewImage: a core-internal tool; it cannot be registered or called back by the client.** `registry.add(ViewImageHandler::new(…))` is registered in core's tool registry (gated by `Feature::ViewImage`, core/src/tools/spec_plan.rs:1230-1234); it is recorded in history as `ViewImageToolCallEvent` (thread_history.rs:386,888), and the client only ever sees an `ImageView` item.

**ephemeral thread**: `ThreadStartParams.ephemeral` (thread.rs:120), used together with `thread/loaded/list` to manage active sessions.

## 5. Usage & limits (tokenCount / rate_limits)

**Push**: each turn pushes `thread/tokenUsage/updated`, payload `ThreadTokenUsageUpdatedNotification{thread_id, turn_id, token_usage}` (v2/thread.rs:1855). `ThreadTokenUsage{total: TokenUsageBreakdown, last: TokenUsageBreakdown, model_context_window: Option<i64>}` (thread.rs:1885-1896, `From<CoreTokenUsageInfo>`). `TokenUsageBreakdown{total_tokens, input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens}` (thread.rs:1913-1933) — i.e. three components, cumulative + most recent + context window, with reasoning tokens broken out separately. The internal experimental channel `rawResponse/completed` attaches the exact usage of a single upstream response (`TokenUsageBreakdown` + `usage_metadata`, thread.rs:1864-1882).

**Pull + push dual channel**: `account/rateLimits/read` returns `GetAccountRateLimitsResponse{rate_limits: RateLimitSnapshot, rate_limits_by_limit_id: Option<HashMap<…>>}` (v2/account.rs:331-338); on change it pushes `account/rateLimits/updated`. `RateLimitSnapshot{limit_id, limit_name, normal_model_slug, primary: Option<RateLimitWindow>, secondary, credits, individual_limit, spend_control_reached, plan_type, rate_limit_reached_type}` (protocol.rs:2326-2340) — primary/secondary windows + credits + spend control. Also present: `account/usage/read` (GetAccountTokenUsage), `account/rateLimitResetCredit/consume`.

## 6. Parts not covered by the App Server (gaps)

Checked item by item against the "full runtime protocol" (v2 in fact covers far more than the rumors suggested):

- **Compaction: covered, but not parameterizable.** `thread/compact/start` params are only `{thread_id}` (v2/thread.rs:1148-1153) + the `thread/compacted` notification; the `ThreadItem::ContextCompaction` item type exists. The client cannot pass a compaction prompt or policy; manual `rollout/compress`, `memory/reset`, `thread/memoryMode/set` are adjacent capabilities.
- **Terminal: covered, and quite complete.** `command/exec` (+write/terminate/resize), `process/spawn|writeStdin|kill|resizePty` (PTY resize!), `thread/backgroundTerminals/list|clean|terminate`, `thread/shellCommand` (preserves shell syntax, **no sandbox, full permissions**, timeout_ms, thread.rs:1160-1172), plus the `item/commandExecution/outputDelta` and `terminalInteraction` notifications (interaction events that write stdin to an existing terminal, item.rs:1496).
- **Background tasks: partial.** Only `thread/queue/*` (queued turns: add/list/update/delete/reorder/start) and backgroundTerminals; a general background task framework was not found in the source.
- **Subagents: no client-side orchestration API, but there is an event surface.** The `ThreadItem::SubAgentActivity` and `CollabAgentToolCall` item types (item.rs:236 section) show subagent activity flowing out as items; the `multiAgentMode` field is deprecated ("Use Ultra reasoning effort for proactive multi-agent behavior", thread.rs:110-111); `approvals_reviewer=auto_review` is a server-internal subagent (shared.rs:243-261); hooks have `subagent_start/subagent_stop` matchers (config.rs:618-621). But the client cannot spawn/configure subagents — no corresponding method was found in the source.
- **File-diff granularity: file-level unified diff.** `turn/diff/updated`, `item/fileChange/patchUpdated` (`FileUpdateChange{path, kind: Add|Delete|Update{move_path}, diff}` v2/item.rs:1135-1152); no hunk-level streaming, no client apply/edit API.
- **Raw model stream: hidden by default.** `rawResponseItem/completed`/`rawResponse/completed` are emitted only when `thread/start.experimentalRawEvents=true` is set (internal use, thread.rs:163-165); additionally `Feature::OmitAppServerNotificationMedia` trims notification media (bespoke_event_handling.rs:1102-1105).
- **Others out of scope**: no LLM sampling/completions proxy interface (a pure agent-session protocol); system-prompt injection only via `base_instructions/developer_instructions` (thread.rs:79-81); error classification only the generic `error`/`warning`/`configWarning`/`deprecationNotice`.

## 7. ARI problems solved vs. unsolved by the App Server + designs worth borrowing

**Solved (with source evidence)**:
1. Transport and framing: line-delimited JSON-RPC (stdio.rs:73,141) + ws/uds/remote-control variants, one protocol over multiple transports.
2. Bidirectional requests and pending-request routing: `send_request→(id, rx)`, Broadcast/ToConnection envelopes (outgoing_message.rs:117,407).
3. Capability negotiation: `initialize` + `experimental_api`/`opt_out_notification_methods`/`extensions` (v1.rs:55-75).
4. Wire-compatible evolution: `#[experimental(...)]` attribute annotation + outbound field stripping, avoiding schema forks (throughout v2/thread.rs; item.rs:1605).
5. Closed approval loop: decision-only responses + session-level cache (AcceptForSession) + rule amendments as first-class decisions (execpolicy/network amendment) + server-declared `available_decisions` + optional machine approver auto_review.
6. Policy layering: thread-level defaults + turn-level overrides (approval/sandbox/model/cwd can all be overridden per turn, turn.rs:207-230).
7. Client-tools inversion: dynamic tools are called back over the same JSON-RPC channel, no side-channel protocol.
8. usage/rate-limit dual channel (pull + push) and three-level coordinate event envelopes (see below).
9. Recoverable history: rollout path + pagination (initialTurnsPage) instead of full hydration.

**Unsolved / still open questions for ARI**: client-side subagent orchestration (only an event surface); modifying the command body at approval time; general background tasks; parameterizable compaction; hunk-level file-edit callbacks; structured error classification (only the error/warning family); multimodal realtime audio is a separate sub-protocol (thread/realtime/*), not unified with the text turn model.

**Designs worth borrowing for ARI**:
- **Naming scheme**: `{domain}/{resource}/{action}` and `{domain}/{resource}/{subresource}/{action}` (thread/turn/start, item/commandExecution/requestApproval); notifications use past participles (updated/changed/completed), requests use bare verbs — directionality is machine-inferrable.
- **Three-level event coordinates**: almost every notification carries `thread_id/turn_id/item_id` (e.g. ReasoningTextDeltaNotification, item.rs:1480-1490), using "session / turn / atomic item" as the correlation keys; ARI's event envelope can adopt this directly.
- **Item as the streaming unit**: 16 ThreadItem kinds + item/started|completed bracketing the deltas, replacing per-tool-type begin/end events.
- **Approval pattern**: params carry `started_at_ms` (UI timing), `reason`, `available_decisions`; the response is a closed enum rather than a boolean; a policy amendment is itself one of the decisions, making "approval = authorization-scope adjustment" explicit.
- **Client-tools inversion**: the client registers tool declarations (thread/start.dynamic_tools + namespace) and the runtime calls back with standard requests — same channel, same envelope, same error semantics as approvals.
- **Experimental feature gating**: method/field-level opt-in + schema export (export.rs), giving protocol evolution a path that avoids breaking changes.
- **Client-controlled notification filtering**: opt_out_notification_methods suppresses by method name, so high-traffic notifications cannot overwhelm the UI.
