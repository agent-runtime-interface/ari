# 03 · Codex CLI (codex-rs) Runtime/Protocol internals deep survey — ARI design reference

> Survey subject: the Rust implementation of the OpenAI Codex CLI (codex-rs), focused on the CLI's own runtime/loop/protocol internals.
> Repository: `codex/` (local clone, not checked into this repo; HEAD `44b857c00e`, 2026-09-22). Does not cover the app-server protocol (cross-referenced separately).
> [source] = source-code evidence (path + symbol); [docs] = repository documentation. All line numbers are based on that HEAD and may be offset relative to released versions.

## 0. Overview: crate map and the three "protocol lines"

The survey is based on HEAD `44b857c00e` (2026-09-22). codex-rs is an extremely large workspace (~180 crates); the core chain relevant to this report:

- **core** (codex-core): agent loop, Session/turn state machine, tool routing (tools/router.rs), approvals (tools/approvals.rs), compaction (compact*.rs), subagent scheduling (agent/). Entry points `CodexThread::submit(Op)`/`next_event()` [core/src/codex_thread.rs:235,658].
- **protocol** (codex-protocol): `Op`, `EventMsg`, `ResponseItem` (via models.rs), `AskForApproval`/`SandboxPolicy`/`ReviewDecision`, `SessionMeta`, and all other wire types.
- **rollout** (codex-rollout) + **history**: JSONL persistence (recorder/state_db/reverse_jsonl_scanner) and the `RolloutItem`/`RolloutLine`/`InitialHistory` definitions.
- **Three protocol lines**: (1) the core event stream (in-process, consumed directly by the TUI); (2) `codex exec --json` (EventMsg → condensed ThreadEvent JSONL, one-way); (3) app-server (bidirectional JSON-RPC, v1/v2, TS binding generation). **The old `codex proto` no longer exists**.
- Remaining periphery: tools (ToolSpec/spec compilation), codex-api (ResponseEvent/SSE), rmcp-client+codex-mcp (MCP), code-mode* (PTC/V8), sandboxing+linux-sandbox+windows-sandbox-rs+execpolicy (sandbox), thread-store/thread-manager (thread store), tui (reference frontend implementation).

Note: in this HEAD many older documentation terms have been renamed — TaskStarted/TaskComplete→TurnStarted/TurnComplete (wire names keep task_*), UserTurn→TurnInput, OnFailure→OnRequest alias, AgentMessageDelta→AgentMessageContentDelta, ReasoningDelta→ReasoningContentDelta.

## 1. Session: creation / resume / persistence / fork / interruption

**Storage**: one JSONL file per thread, directory layout `~/.codex/sessions/YYYY/MM/DD/rollout-YYYY-MM-DDThh-mm-ss-<uuid>.jsonl` [rollout/src/list.rs:437 doc; constants `SESSIONS_SUBDIR="sessions"`, `ARCHIVED_SESSIONS_SUBDIR="archived_sessions"`, rollout/src/lib.rs:84-85]. There is also a SQLite index/state database [rollout/src/state_db.rs:47 `try_init_with_roots`] and a reverse JSONL scanner (reads from the tail) [rollout/src/reverse_jsonl_scanner.rs].

**Line format**: `RolloutLine { timestamp: String, ordinal: Option<u64>, #[serde(flatten)] item: RolloutItem }` [history/src/lib.rs:302-308]. A comment states explicitly that RolloutLine does not implement Deserialize and readers must go through codex_rollout's canonical parser to preserve nested decimals (lib.rs:297-300). `RolloutItem` variants [lib.rs:159-175]: SessionMeta / ResponseItem(ResponseItemEnvelope)/ InterAgentCommunication(_Metadata)/ Compacted(CompactedItem)/ TurnContext / TokenUsageRecord / WorldState / SecurityRiskScore / RetainedContext / EventMsg / RealtimeItem. Write side: `RolloutRecorder::record_canonical_items`, `flush`, `append_rollout_item_to_path` [rollout/src/recorder.rs:1035,1074,2005]; `RolloutRecorder::resume(path)` reopens an existing file and continues appending (recorder.rs:365).

**Session identity**: `SessionMeta` [protocol/src/protocol.rs:3100-3175]: `session_id: SessionId` is always equal to the root thread ID; `id: ThreadId` is a UUIDv7 [protocol/src/thread_id.rs:30 `Uuid::now_v7()`]; `forked_from_id`, `forked_from_ordinal_exclusive`, `parent_thread_id` (subagent ownership), `agent_nickname/agent_role/agent_path` (AgentControl subagents), `base_instructions`, `dynamic_tools`, `history_base`, `subagent_history_start_ordinal`, `multi_agent_version`, `context_window`.

**resume**: `codex resume [SESSION_ID|--last|--all|--include-non-interactive]` (picker by default) [cli/src/main.rs:202-203,350, `finalize_resume_interactive`:2557]. Core path: `ThreadManager::resume_thread_from_rollout` [core/src/thread_manager.rs:1195] → `initial_history_from_rollout_path` → `resume_thread_with_history` (:1252) → `spawn_thread`, injecting `InitialHistory::Resumed(ResumedHistory{conversation_id, history, rollout_path})` into StartThreadOptions [history/src/lib.rs:311-323]. resume can also restore token usage from `CompactedItem.latest_token_usage_record` without any arbitrary scan-back [lib.rs:242-246 doc].

**fork**: `codex fork [SESSION_ID|--last]` (main.rs:220, `finalize_fork_interactive`:2592; `--worktree` requires an explicit session id, main.rs:2181). Core: `fork_thread`/`fork_thread_from_history`/`fork_prepared_thread`/`fork_internal_session` [thread_manager.rs:1423,1457,1478,1062], internally `start_thread_inner(options, Some(forked_from_thread_id))` (:1191). Semantics = `InitialHistory::Forked(Vec<RolloutItem>)` + a new ThreadId + `SessionMeta.forked_from_id` (`InitialHistory::forked_from_id`, lib.rs:334).

**crash recovery**: based on append-only JSONL + `recorder.resume(path)` continuation + reverse-scanner tail recovery; the CLI's fatal exit message directly prints a `codex resume <uuid>` hint [cli/src/main.rs:3790 area exit-message logic; utils/cli/src/resume_command.rs:6 `resume_command` generates the hint]; cli/src/state_db_recovery.rs additionally handles state-database recovery. `InitialHistory::Cleared` supports clearing and then continuing the same thread (lib.rs:318-323).

## 2. Message model: the three-layer type system (ResponseItem / ResponseEvent / EventMsg)

Codex divides a "message" into three layers, converging layer by layer:

1. **`ResponseItem`** [protocol/src/models.rs:1011 `pub enum ResponseItem`] — model wire protocol entries (message / function_call / function_call_output / reasoning / custom_tool_call(_output) / local_shell_call, etc.); serves both as the input sent to the model and as the rollout record unit.
2. **`ResponseEvent`** [codex-rs/codex-api/src/common.rs:80 `pub enum ResponseEvent`] — internal events after decoding the model SSE stream (consumed by core only).
3. **`EventMsg`** [protocol/src/protocol.rs:1341] — the client-facing stable event enum; core/src/event_mapping.rs handles the mapping from internal state → EventMsg and its broadcast.

### Full table of EventMsg variants (protocol.rs:1341-1558, serde snake_case tag)

**Lifecycle**: `Error(ErrorEvent)` submission execution error; `Warning` warning (turn continues); `TurnStarted` (serde rename `task_started`, alias `turn_started`) turn start; `TurnComplete` (`task_complete`) all actions finished; `TurnAborted` interruption; `ShutdownComplete`; `SessionConfigured` ack; `ThreadSettingsApplied` thread configuration override has taken effect; `DeprecationNotice`.

**Model output stream**: `AgentMessage` full message; `AgentMessageContentDelta` incremental text (note: the old name AgentMessageDelta has evolved into this variant); `AgentReasoning` reasoning summary; `AgentReasoningRawContent` raw CoT; `AgentReasoningSectionBreak` new reasoning section; `ReasoningContentDelta`/`ReasoningRawContentDelta` reasoning deltas; `PlanDelta`/`PlanUpdate(UpdatePlanArgs)` plan; `ItemStarted`/`ItemCompleted` generic item lifecycle; `RawResponseItem`/`RawResponseCompleted` raw response item passthrough.

**Command execution**: `ExecCommandBegin` a command is about to execute; `ExecCommandOutputDelta` incremental output chunks while running; `TerminalInteraction` writes stdin to a running command and observes stdout; `ExecCommandEnd`; `ViewImageToolCall` view_image attaches a local image.

**File patches**: `ApplyPatchApprovalRequest` patch approval request; `PatchApplyBegin` patch about to be applied (mirrors ExecCommandBegin so the frontend can show progress); `PatchApplyUpdated` latest structured changes generated by the model; `PatchApplyEnd` completion; `TurnDiff` diff for the entire turn.

**Approval/input requests**: `ExecApprovalRequest` command approval; `RequestPermissions` permission request; `RequestUserInput` structured user input; `ElicitationRequest` MCP elicitation; `DynamicToolCallRequest`/`DynamicToolCallResponse` dynamic tool callbacks; `GuardianAssessment` structured lifecycle of the guardian auto-approval review; `GuardianWarning`.

**MCP/search/generation**: `McpStartupUpdate`/`McpStartupComplete` MCP startup progress; `McpToolCallBegin`/`McpToolCallEnd`; `WebSearchBegin`/`WebSearchEnd`; `ImageGenerationBegin`/`ImageGenerationEnd`.

**Usage/context**: `TokenCount(TokenCountEvent)` session usage update (optional = unknown; the UI should not display it); `ContextCompacted` history was compacted (automatically or manually); `ThreadRolledBack` legacy persistence marker for dropping the most recent N user turns (only used for old rollout replay).

**Multi-agent**: `CollabAgentSpawnBegin/End`, `CollabAgentInteractionBegin/End`, `CollabWaitingBegin/End`, `CollabCloseBegin/End`, `CollabResumeBegin/End` (collab interactions); `SubAgentActivity` path-based v2 subagent activity; `HookStarted`/`HookCompleted` lifecycle hooks.

**Other**: `StreamError` model stream error/disconnect; the system is handling it (e.g. backoff retry); `ModelReroute` model routing was changed; `ModelVerification` the backend requires additional account verification; `TurnModerationMetadata`/`SafetyBuffering` safety-moderation metadata and buffering; `AuthRecoveryStarted/Completed` auth recovery; `EnvironmentConnected/Disconnected` environment connection handshake; `ThreadGoalUpdated`/`ThreadQueueChanged` goal and queue; `McpStartupUpdate` and others; `RealtimeConversation*` (Started/Realtime/Closed/Sdp/ListVoicesResponse) voice sessions; `EnteredReviewMode`/`ExitedReviewMode` review mode.

> Vocabulary evolution: TaskStarted/TaskComplete, AgentMessageDelta, and AgentReasoningDelta from the task-era documentation correspond, in this HEAD, to TurnStarted/TurnComplete (wire names still task_started/task_complete), AgentMessageContentDelta, and ReasoningContentDelta respectively.

## 3. Agent Loop: turn entry, model stream, tool dispatch, retries, interruption

**Submission entry**: `CodexThread::submit(op: Op) -> CodexResult<String>` returns a submission id [core/src/codex_thread.rs:235 → io.submit; the old Submission{id,op} wrapper no longer exists, Op is submitted directly]. Ops are dispatched by SessionIo/handlers [core/src/session/handlers.rs:427 `Op::Interrupt`].

**Task layer**: `TaskKind { Regular, Review, Compact }` [core/src/state/turn.rs:68]; task implementations `RegularTask`/`ReviewTask`/`CompactTask`/`UserShellCommandTask` [core/src/tasks/mod.rs:62-67]. `RunningTask { kind, task, cancellation_token: CancellationToken, handle: AbortOnDropHandle, turn_context }` [state/turn.rs:74-85] — one CancellationToken per turn.

**Turn entry**: `run_turn(sess, turn_context, input, …, cancellation_token)` [core/src/session/turn.rs:163]: guardian pending-input check (:171) → `run_pre_sampling_compact` pre-sampling pre-compaction (:183; on failure the user input is recorded first, then the error is raised) → `required_mcp_servers_for_input` starts MCP on demand (:235) → `build_prompt` (:1555) → `run_sampling_request` (:1584).

**Sampling loop**: `try_run_sampling_request` [turn.rs:2448]: `client_session.stream(...).or_cancel(&cancellation_token)` (:2484-2501); `loop { stream.next() }` consumes `ResponseEvent`: Created{response_id} records the response id (:2575); OutputItemDone(item) → `handle_output_item_done` (:2672) returns `output_result.tool_future` → `in_flight.push_back(tool_future)` (:2679-2681). **Parallel tool calls**: `let mut in_flight: FuturesOrdered<InFlightFuture>` [turn.rs:2502] — multiple function_calls within the same response execute concurrently and are drained at the loop tail; the `needs_follow_up` flag decides whether to issue another sampling round (:2685). An assistant Commentary message or a Reasoning item can preempt input waiting in the mailbox (`preempt_for_mailbox_mail`, :2648-2669). If the stream closes without a response.completed → `CodexErr::Stream` (:2562-2566).

**Tool dispatch**: `ToolRouter::dispatch_tool_call_with_state` / `dispatch_tool_call_with_code_mode_result` [core/src/tools/router.rs:323,300]; approval rejection `ReviewDecision::Abort → ToolError::Codex(CodexErr::TurnAborted)` [core/src/tools/approvals.rs:467]. `TurnState.tool_calls` counter [state/turn.rs:99].

**Retries (backoff)**: `core/src/responses_retry.rs`: constants `INITIAL_CONNECTION_RETRY_DELAY=5s`, `MAX_CONNECTION_RETRY_DELAY=60s` (:16-17), `max_retries: u64` (:52), log "stream disconnected - retrying sampling request ({retries}/{max_retries} in {delay:?})" (:163). During retries it emits `EventMsg::StreamError` (doc: "retrying with backoff", protocol.rs:1490-1492). The backoff utilities have moved to the codex-async-utils crate [core/src/util.rs:1 `pub use codex_async_utils::backoff`].

**Interruption**: the client submits `Op::Interrupt` (handlers.rs:427; doc: responds with EventMsg::TurnAborted, protocol.rs:586). Every await inside the loop uses `.or_cancel(&cancellation_token)`; cancellation → `CodexErr::TurnAborted` (turn.rs:2554-2555). `TurnAbortReason { Interrupted, Replaced, ReviewEnded, BudgetLimited }` [protocol.rs:4253-4258]; `abort_turn_if_active(turn_id, reason)` [tasks/mod.rs:566] flushes the interrupted-turn history marker first, then emits the TurnAborted event (tasks/mod.rs:962-989 comment: some clients depend on the ordering). Grace period `GRACEFULL_INTERRUPTION_TIMEOUT_MS=100` [tasks/mod.rs:69]. TUI ESC key binding: not found in the source (tui layer not verified).

**max turns / token budget**: `max_turns` limit: not found in the source. Budget abort goes through `TurnAbortReason::BudgetLimited` [protocol.rs:4257], with exhaustion decided by the backend-reported `usage.codex_rollout_budget_units` [core/src/rollout_budget.rs:47-56 `RolloutBudgetReminder`]; compaction has its own separate token budget [core/src/compact_token_budget.rs].

Tool discovery/exposure: core/src/mcp_tool_exposure.rs, tools/src/tool_discovery.rs; tools/src/mcp_tool.rs is the ToolSpec adapter for MCP tools.

## 5. Human-in-the-loop: approval policy, sandbox, and escalation

**Approval policy**: `AskForApproval` [protocol/src/protocol.rs:969-992, kebab-case serde]: `UnlessTrusted` (serde `untrusted`; untrusted items require approval by default unless an execpolicy rule allows them), `OnRequest` (#[default]; the model decides when to ask; `#[serde(alias = "on-failure")]` — the old OnFailure has been merged in as an alias; no standalone OnFailure variant was found in the source), `Granular(GranularApprovalConfig)` (fine-grained switches: sandbox_approval / rules / skill_approval / request_permissions / mcp_elicitations, protocol.rs:995-1009), `Never` (failures are returned directly to the model, no escalation).

**Sandbox policy**: `SandboxPolicy` [protocol.rs:1055-1103, serde tag="type", kebab-case]: `danger-full-access`, `read-only{network_access}`, `external-sandbox{network_access}` (the host is already inside an external sandbox; full-disk read + specified network allowed), `workspace-write{writable_roots, network_access, exclude_tmpdir_env_var, exclude_slash_tmp}`. Auxiliary layer: `SandboxMode { ReadOnly | WorkspaceWrite | DangerFullAccess }` (kebab-case) [protocol/src/config_types.rs:104-114]; `WritableRoot { root, read_only_subpaths, protected_metadata_names }` blocks writes to privilege-escalating paths such as `.git/hooks` and `.codex` [protocol.rs:1111-1156]; `NetworkAccess { Restricted, Enabled }` (protocol.rs:1039). Platform implementations: codex-rs/sandboxing (landlock/seatbelt via manager.rs/policy_transforms.rs), linux-sandbox, windows-sandbox-rs, bwrap, execpolicy, shell-escalation — each is its own crate.

**Escalation request flow**:
1. Before tool execution, `Session::request_command_approval` ([core/src/session/mod.rs:2866-2887]): first inserts `tx_approve: oneshot::Sender` into `active_turn.turn_state.pending_approvals` (state/turn.rs:90 `HashMap<String, oneshot::Sender<ReviewDecision>>`), then emits `EventMsg::ExecApprovalRequest(ExecApprovalRequestEvent{call_id, approval_id, turn_id, command, cwd, reason, kind, network_approval_context, proposed_execpolicy_amendment, proposed_network_policy_amendments, additional_permissions, available_decisions, parsed_cmd, model_context, …})`, then `rx_approve.await.unwrap_or(ReviewDecision::Abort)` (mod.rs:2887) — no answer from the client is treated as Abort.
2. Same shape for patches: `request_patch_approval` → `ApplyPatchApprovalRequest{call_id, changes: HashMap<PathBuf, FileChange>, reason, grant_root}` (mod.rs:2894-2930).
3. **Decision return**: the client submits `Op::ExecApproval { id(approval_id), turn_id, decision: ReviewDecision }` [protocol.rs:655-662] → handlers.rs:529 → `exec_approval()` [handlers.rs:173-202]: for ApprovedExecpolicyAmendment it first runs `persist_execpolicy_amendment`; `ReviewDecision::Abort` → `sess.interrupt_task()` (turn-level abort); everything else → `sess.notify_approval(&approval_id, decision)` wakes the pending oneshot. `Op::PatchApproval` takes the same path (handlers.rs:537-540, 204-211).

**Decision enum**: `ReviewDecision` [protocol.rs:4136-4171, snake_case]: `Approved`, `ApprovedExecpolicyAmendment{proposed_execpolicy_amendment}`, `ApprovedForSession` (session-level approval cache), `ApprovedMcpPolicyAmendment`, `NetworkPolicyAmendment{network_policy_amendment}` (persistent per-host allow/deny), `Denied{rejection}` (rejected, but the session continues), `TimedOut` (the auto-approval review timed out), `Abort` (rejected and stopped until the next user command). Default = Denied. Guardian auto-approval reviews can produce a GuardianAssessment event; the user can use `Op::ApproveGuardianDeniedAction` to override a rejection once (protocol.rs:734).

## 6. File/Diff: how file changes reach the client

**Change unit**: `FileChange` [protocol/src/protocol.rs:4212-4223]: `Add{content}` / `Delete{content}` / `Update{unified_diff, move_path}`; appears as `HashMap<PathBuf, FileChange>` in `ApplyPatchApprovalRequestEvent.changes` (approval preview, mod.rs:2898) and `PatchApplyBeginEvent/EndEvent.changes`. Patch lifecycle: `PatchApplyBegin` (about to apply) → `PatchApplyUpdated` (latest structured changes generated by the model, may fire multiple times) → `PatchApplyEnd{call_id, turn_id, stdout, stderr, success, changes, status: Completed|Failed|Declined}` [protocol.rs:3721-3747]. The Declined status is the explicit closure after an approval rejection. Turn-level summary: `TurnDiffEvent { unified_diff: String }` [protocol.rs:3750-3752], aggregated by core/src/turn_diff_tracker.rs (gated by `should_emit_turn_diff` in the §3 sampling loop). In the `exec` JSONL protocol the corresponding items are FileChangeItem/FileUpdateChange (exec_events.rs). The apply_patch implementation and spec are a standalone crate: codex-rs/apply-patch (core/src/apply_patch.rs + handlers/apply_patch_spec.rs).

## 7. Command/Terminal: exec event stream and background commands

**Event fields**: `ExecCommandBeginEvent { call_id, turn_id, command: Vec<String>, cwd: PathUri, parsed_cmd: Vec<ParsedCommand>, source: ExecCommandSource(default Agent), process_id (PTY process identifier), plugin_id/script_path (plugin provenance), interaction_input (unified exec interaction input), started_at_ms }` [protocol.rs:3539-3570]; `ExecCommandEndEvent { call_id, completed_at_ms, …exit code/duration }` (:3573-). Incremental output goes through `ExecCommandOutputDelta` (3643, per chunk).

**Interaction and background**: `TerminalInteractionEvent` = writes stdin to a running command and observes stdout (protocol.rs:1461-1462); the unified_exec handlers (core/src/unified_exec/, tools/handlers/unified_exec/) maintain persistent PTY sessions, with `process_id` correlating the underlying process. Background terminal processes are **not** terminated when a turn is interrupted — the `Op::Interrupt` doc states explicitly "without terminating background terminal processes"; an explicit `Op::CleanBackgroundTerminals` is required [protocol.rs:585-591]; query interface `list_background_terminals` [tasks/mod.rs:782, telemetry TURN_UNIFIED_EXEC_RUNNING_PROCESSES_METRIC]; codex_thread.rs:27 references `BackgroundTerminalInfo`. User-direct shell: `Op::RunUserShellCommand{command, timeout_ms}` ("!" prefix, 1h default; output likewise flows through the ExecCommand* events, and TurnComplete is emitted at the end) [protocol.rs:744-749; tasks/user_shell.rs UserShellCommandTask/Mode].

## 8. Context management: compaction, truncation, and rollout recovery

**Threshold evaluation**: `ContextWindowTokenStatus` [core/src/session/context_window.rs:8-20]: `active_context_tokens` (session-wide token total), `auto_compact_scope_limit` (= config `model_auto_compact_token_limit` or `model_info.auto_compact_token_limit()`; the scope can be `Total` or `BodyAfterPrefix` — counting only the increment after the initial prefix, :61-81), `full_context_window_limit = resolved_context_window × effective_context_window_percent / 100` (:84-86, percentage buffer), `token_limit_reached`, `turn_end_compaction_threshold_reached` (also checked at turn end). Context window source: the `Config.model_context_window` override (clamped to the model's maximum, models-manager/src/model_info.rs:20, model_info_tests.rs:251); otherwise the model metadata is used.

**Trigger path**: `run_pre_sampling_compact` [core/src/session/turn.rs:1271-1300] is called at turn entry (before run_turn): first `maybe_run_previous_model_inline_compact` (:1339 — when the model switches, if comp_hash changed or the new window is smaller, a finalizing compaction runs against the old model), then checks `token_status.token_limit_reached` → `run_auto_compact(reason=ContextLimit, phase=PreTurn)` (:1288-1297).

**Compaction implementation**: `run_auto_compact` [turn.rs:1443-1501] has three branches: (1) Feature::TokenBudget → `compact_token_budget::run_inline_auto_compact_task`; (2) provider supports RemoteCompaction::V2 → `run_inline_remote_auto_compact_task_v2` (server-side compaction); (3) otherwise local `run_inline_auto_compact_task` (core/src/compact.rs:114-144) — starts a compact task with `SUMMARIZATION_PROMPT` or the config `compact_prompt` as input. Manual trigger: `Op::Compact` → `run_compact_task` (trigger=Manual, reason=UserRequested, phase=StandaloneTurn, emitting turn_started first, compact.rs:146-163). Compaction tasks have PreCompact/PostCompact hooks (`run_pre_compact_hooks`; Stopped → CodexErr::TurnAborted, compact.rs:185-200) and `CompactionTrigger/Reason/Phase/Implementation` metadata; separate token budget [core/src/compact_token_budget.rs].

**Result and multi-window**: the artifact is `CompactedItem { message, replacement_history, window_number/first_window_id/previous_window_id/window_id, compaction_response_id, latest_token_usage_record, guardian_history, retained_context, mcp_resource_origins }` [history/src/lib.rs:230-247] — the window id chain supports paginated history (ThreadHistoryMode::Paginated, protocol.rs:762-766); on the Responses API side there are the `ContextCompaction`/`Compaction`/`CompactionTrigger` ResponseItem variants. Events: `EventMsg::ContextCompacted` (protocol.rs:1383); dedicated tools `get_context_remaining` (remaining quota) and `new_context_window` (reopen window, handlers/ directory).

**Truncation/recovery**: on the rollout side, thread_rollout_truncation.rs + the reverse scanner support truncation recovery; `ThreadRolledBack` is a legacy replay marker (live rollback not supported, protocol.rs:1385-1387); on resume, history is fully rebuilt from `RolloutItem`s (including Compacted/EventMsg/TokenUsageRecord, see §1).

## 9. PTC (programmatic tool calling): Code Mode

**It exists.** Implemented as a standalone code-mode crate family: codex-rs/code-mode (sessions: grpc_session / remote_session), code-mode-runtime (cell_actor / session_runtime / service.rs / **v8_init.rs** — the V8 JS runtime), code-mode-protocol, code-mode-host, code-mode-protocol-noop-macros, plus a v8-poc prototype directory.

**Mechanism**: tool specs are augmented and then injected into the code runtime — `augment_tool_spec_for_code_mode` [tools/src/code_mode.rs:7-40] attaches code-mode exec sample descriptions to Function/Freeform/Namespace tools and generates nested call names; code-mode-protocol provides `render_json_schema_to_typescript` (converts a tool's JSON Schema into TS declarations for the model to write code against), `CODE_MODE_PRAGMA_PREFIX`, `CodeModeNestedToolCall`, `DEFAULT_EXEC_YIELD_TIME_MS`/`DEFAULT_MAX_OUTPUT_TOKENS_PER_EXEC_CALL` [code-mode-protocol/src/lib.rs export table]. The model submits JS code in a single exec call; the runtime executes it and issues nested tool calls to the host at yield points, routed back to the real tools by core's `ToolRouter::dispatch_tool_call_with_code_mode_result` [core/src/tools/router.rs:300,346]. In short: **Codex's PTC = "tool JS/TS-ification + V8 code execution + nested tool-call loop-back"**, gated by a feature flag and provider capability (core/tests/suite/code_mode.rs has end-to-end tests).

## 10. Subagents: collab / multi-agent

**Natively present, two generations of implementation.** Event surface: `EventMsg::CollabAgentSpawnBegin/End`, `CollabAgentInteractionBegin/End`, `CollabWaitingBegin/End`, `CollabCloseBegin/End`, `CollabResumeBegin/End` + v2's `SubAgentActivity` [protocol/src/protocol.rs:1535-1557].

**Tool set** [core/src/tools/handlers/multi_agents_spec.rs]: `spawn_agent` (v1/v2, with model/agent_type/reasoning/fork_turns=none|all options; outputs the agent thread id + a user-facing nickname + a canonical task name such as `/root/task1/task_3`; the v2 description states explicitly that "the spawned agent has the same tools as you and can continue spawning subagents", :761-768), `send_message` (:185-203), `resume_agent` (:246-263, revives a closed agent), `wait_agent` (v1: waits for a specified agent to finish and returns its result; v2: mailbox update summary + supports user-input preemption, :287), `close_agent` (:317-328, cascades close to descendants), and interrupt by id/task-name. Multi-generation concurrency limits and scheduling live in core/src/agent/ (control.rs AgentControl, status.rs, communication).

**Session side**: a subagent is a real thread — SessionMeta records `parent_thread_id`, `agent_nickname/agent_role/agent_path`, `subagent_history_start_ordinal` (inherits the parent context but projects its own history), `multi_agent_version` [protocol.rs:3100-3175]; InterAgentCommunication becomes an Op and a RolloutItem (protocol.rs:790-806, records inter-agent message history; trigger_turn decides whether to trigger the recipient's turn); after resuming the parent thread, `ensure_multi_agent_v2_child_loaded` can reload child threads [thread_manager.rs:1218-1249]. InterAgentCommunicationMetadata records trigger_turn.

## 11. Streaming: what the client sees during a turn + Usage/Reasoning events

**Sequence** (a normal turn as seen by the client via next_event/the event stream): `TurnStarted` (wire name task_started; includes model_context_window, collaboration_mode, etc., docs/protocol_v1.md:80) → [if compacting] `ContextCompacted` → streamed output: `AgentMessageContentDelta` (body deltas) / `AgentReasoning` / `ReasoningContentDelta` / `ReasoningRawContentDelta` / `AgentReasoningSectionBreak` (reasoning sectioning) / `PlanDelta` / `ItemStarted`→`ItemCompleted` (generic item lifecycle) / `RawResponseItem` (passthrough) → tool phase: `ExecCommandBegin`→`ExecCommandOutputDelta`*→`ExecCommandEnd`, `PatchApplyBegin/Updated/End`, `McpToolCallBegin/End`, `WebSearchBegin/End`, `ViewImageToolCall`, approval requests → `TokenCount` (on every usage update; `should_emit_token_count` is gated by the sampling loop, turn.rs:2511) → `TurnDiff` (turn-level file-change summary, turn_diff_tracker.rs) → `TurnComplete` (or `TurnAborted`/`Error`). Assistant messages in the Commentary phase support preempting the mailbox queue (§3).

**TokenCount payload**: `TokenCountEvent { info: Option<TokenUsageInfo>, rate_limits: Option<RateLimitSnapshot> }` [protocol.rs:2320-2323; doc: Optional = unknown, the UI should not display it]. `TokenUsageInfo { total_token_usage, last_token_usage, model_context_window }` [protocol.rs:2253-2259] (TokenUsage contains input/cached_input/cache_write_input/output/reasoning_output/total; the telemetry field list at tasks/mod.rs:726-771 corroborates this). `RateLimitSnapshot { primary, secondary: RateLimitWindow{used_percent, window_minutes, resets_at}, credits, plan_type, rate_limit_reached_type, spend_control_reached, … }` [protocol.rs:2326-2351,2369-2378]. `fill_to_context_window` (:2293) converts the remaining headroom after compaction into usage measured against a full window.

**Reasoning side**: the model produces `ResponseItem::Reasoning{summary, content, encrypted_content}` (models.rs:1047-1059; encrypted_content enables replay under Zero-Data Retention); the streamed deltas are `ReasoningContentDelta`/`ReasoningRawContentDelta`; the `AgentReasoning*` event family is the summary presentation. The ConcurrentReasoningSummaries feature (turn.rs:2479-2483) allows the summary and the body to stream concurrently.

**Persistence**: TokenUsageRecord is its own RolloutItem (lib.rs:168); on resume, cumulative usage can be restored from CompactedItem.latest_token_usage_record (§1).

## 12. Transport: the CLI's event outlets as a program (stdio / exec JSONL / proto)

**Core event outlet**: `Session` holds an `async_channel::unbounded()` event channel [core/src/session/mod.rs:590 `let (tx_event, rx_event) = async_channel::unbounded();`; send site :2585 `tx_event.send(event)`; `Event { id: String(submission/turn id), msg: EventMsg }`]. External API: `CodexThread::next_event() -> CodexResult<Event>` [core/src/codex_thread.rs:658] + `submit(Op) -> CodexResult<String>` (:235). This is core's "client protocol": Op submission / Event streamed replies.

**TUI**: in-process direct connection — `tui::Tui` wraps the core event stream with `TuiEventStream`/`EventBroker` [tui/src/tui.rs:55-56,943 `pub fn event_stream(&self) -> Pin<Box<dyn Stream<Item = TuiEvent>>>`; reconnect recovery `resume_events` tui.rs:820]. No IPC serialization; EventMsg is consumed directly.

**`codex exec --json` (JSONL mode)**: `codex exec` non-interactive mode emits JSON events line by line on stdout — `EventProcessorWithJsonOutput` maps core `EventMsg` to a more condensed `ThreadEvent` sequence [exec/src/event_processor_with_jsonl_output.rs:59-80; event types exec/src/exec_events.rs: ThreadStartedEvent / ItemStartedEvent / ItemUpdatedEvent / ItemCompletedEvent / TurnStartedEvent / TurnCompletedEvent / TurnFailedEvent / ThreadErrorEvent / Usage; item types: AgentMessageItem / ReasoningItem / CommandExecutionItem / FileChangeItem / McpToolCallItem / PatchApplyStatus+PatchChangeKind / WebSearchItem / TodoListItem / CollabToolCallItem]. There is also EventProcessorWithHumanOutput (human-readable). In short: **the CLI's JSON event protocol outlet = `codex exec --json`, not the old `codex proto`** — the proto subcommand in this HEAD: not found in the source.

**app-server (JSON-RPC)**: `codex app-server` [cli/src/main.rs:169-172 "[experimental] Run the app server"] + app-server-daemon (remote control). The protocol lives in codex-rs/app-server-protocol: two versions, v1 and v2; the v2 spec (camelCase wire, `*Params/*Response/*Notification`, `<resource>/<method>` such as thread/start, `#[ts(export_to = "v2/")]` TS binding generation; see AGENTS.md and the cli/src/main.rs:617-620 generate-ts/json-schema commands). app-server internally converts EventMsg into ServerNotification (v2) pushes — the exec JSONL processor likewise imports codex_app_server_protocol types (event_processor_with_jsonl_output.rs:6-16); the two protocols share the item abstraction.

**Historical comparison**: `codex proto` in early versions = the stdin/stdout JSONL Submission/Op↔Event protocol; in this HEAD its role is split three ways: (a) in-process channel, (b) `codex exec --json` one-way JSONL, (c) app-server bidirectional JSON-RPC.

## 14. Judgments: what the Shell must see vs Runtime internals

1. **The Shell must see turn lifecycle boundaries**: TurnStarted/TurnComplete/TurnAborted/Error — without them the UI state machine cannot be aligned; the wire names are task_started/task_complete (compatibility aliases turn_started/turn_complete), and integrations must parse by the serde names [protocol.rs:1391,1400].
2. **The Shell must see two streaming channels**: assistant text (AgentMessageContentDelta) and reasoning (ReasoningContentDelta) are independent event families and must not be merged; reasoning also has SectionBreak segmentation semantics [protocol.rs:1530-1533].
3. **The Shell must see approval request-response pairs**: on the event side ExecApprovalRequest/ApplyPatchApprovalRequest (with approval_id/call_id, available_decisions, proposed amendments), and on the response side Op::ExecApproval/PatchApproval{decision}; timeout/no answer = Abort — the protocol must support "a wait that can be cancelled" [session/mod.rs:2887; protocol.rs:4170].
4. **The Shell must see the structured file-change stream**: PatchApplyBegin(changes)→End(changes+status Completed/Failed/Declined)+TurnDiff{unified_diff}; watching only the apply_patch tool output is not enough — changes must be available for preview before approval [protocol.rs:3721-3747,2894].
5. **The Shell must see usage and quota**: TokenCount's rate_limits (primary/secondary/credits) is the only quota signal; model context window occupancy (model_context_window) is delivered with info and is used to render the remaining headroom [protocol.rs:2253-2259].
6. **The Shell must see session resumability**: crash recovery depends on rollout JSONL + the `codex resume <uuid>` hint; a Shell integration that wants to persist sessions should persist the rollout path/ThreadId rather than assembling history itself [cli/main.rs:3790].
7. **The Shell must see the three-phase shape of tool execution**: Begin (with parsed_cmd/cwd)→OutputDelta→End (exit code/duration), plus McpToolCallBegin/End as the equivalent events for MCP — this is the minimal set for rendering "what is happening right now" [protocol.rs:1455-1464].
8. **Can be internalized: model stream decoding and retries.** SSE decoding, the 5s→60s backoff, and stream disconnected retries all live inside core; the client only receives StreamError (carrying "retrying" semantics); the Shell does not need to implement 429/5xx backoff itself [responses_retry.rs:16-17,163].
9. **Can be internalized: parallel tool scheduling.** FuturesOrdered concurrency, in-flight ordering, and the needs_follow_up decision are all runtime internals; the client only needs to see the three-phase events completing out of order [turn.rs:2502].
10. **Can be internalized: compaction decisions.** When to compact, local vs remote-v2, and window chain management are transparent to the client — there is only a single ContextCompacted event; the Shell should not truncate history on its own, or it breaks rollout replay [turn.rs:1443-1501].
11. **Can be internalized: context construction.** build_prompt, on-demand MCP startup, skills/plugins injection, and the ContextualUserFragment constraints (AGENTS.md: context is append-only and never modified, each item ≤10K tokens) all live in core; user input submitted by the Shell is normalized before being persisted.
12. **Can be internalized (but is subscribable): guardian auto-approval.** GuardianAssessment/ApproveGuardianDeniedAction is an optional override path; under the default policy the client need not participate in auto reviews [protocol.rs:734,1484].
13. **Protocol shape judgment**: Codex has no "single CLI protocol" but three outlets (the in-process core Event stream, `codex exec --json` one-way JSONL, app-server bidirectional JSON-RPC v2); if ARI wants to reuse this, align with app-server v2 (camelCase, thread/<method>, TS binding generation) rather than replicating the deleted proto pattern [exec/event_processor_with_jsonl_output.rs:59; cli/main.rs:169].
14. **Vocabulary judgment**: the Task→Turn rename (TurnStarted/TurnComplete), the UserTurn→TurnInput renaming, and the OnFailure→OnRequest alias show that codex-rs's protocol semantics are migrating from "task-driven" to "turn/thread-driven"; ARI's design should directly adopt the thread/turn/item three-layer vocabulary [protocol.rs:1391-1401,612-616,977].
15. **Budget judgment**: no max_turns hard limit; interruptions have four reasons (Interrupted/Replaced/ReviewEnded/BudgetLimited), where BudgetLimited comes from the backend-reported rollout budget units — if ARI does budget control, it should be designed as "a revocable external budget signal at runtime" rather than a local counter [protocol.rs:4253-4258; rollout_budget.rs:47-56].
