# 08 · Related work and secondary subjects — source-level survey (part 2): Claude Code Agent SDK / CLI and Gemini CLI

> Status: complete
> Method and limitations (important): the Claude Code CLI itself is closed-source, a packaged and obfuscated npm distribution; **this report does not perform a source audit of the CLI binary**. Its protocol evidence comes from (a) the type declarations `sdk.d.ts` shipped inside the npm package `@anthropic-ai/claude-agent-sdk` (9451 lines, the public API surface, marked as [source: npm sdk.d.ts]), (b) the official code.claude.com documentation [docs], and (c) the open-source repository `anthropics/claude-agent-sdk-typescript`. ## 1. Claude Code: the Agent SDK and the headless CLI protocol

### 1.1 Message model (stream-json / SDKMessage)

The authoritative message union is `SDKMessage` [source: npm sdk.d.ts:5025], with members (38 of them, listed one by one to show how large the runtime event surface is):

`SDKAssistantMessage | SDKUserMessage | SDKUserMessageReplay | SDKResultMessage | SDKSystemMessage | SDKPartialAssistantMessage | SDKCompactBoundaryMessage | SDKStatusMessage | SDKAPIRetryMessage | SDKControlRequestProgressMessage | SDKModelRefusalFallbackMessage | SDKModelRefusalNoFallbackMessage | SDKLocalCommandOutputMessage | SDKHookStartedMessage | SDKHookProgressMessage | SDKHookResponseMessage | SDKPluginInstallMessage | SDKToolProgressMessage | SDKAuthStatusMessage | SDKTaskNotificationMessage | SDKTaskStartedMessage | SDKTaskUpdatedMessage | SDKTaskProgressMessage | SDKBackgroundTasksChangedMessage | SDKThinkingTokensMessage | SDKSessionStateChangedMessage | SDKWorkerShuttingDownMessage | SDKCommandsChangedMessage | SDKNotificationMessage | SDKFilesPersistedEvent | SDKToolUseSummaryMessage | SDKMemoryRecallMessage | SDKRateLimitEvent | SDKElicitationCompleteMessage | SDKPermissionDeniedMessage | SDKPromptSuggestionMessage | SDKMirrorErrorMessage | SDKInformationalMessage | SDKConversationResetMessage`

**Model API messages vs harness runtime events** — the distinction (a key perspective for ARI design):
- Payloads that are raw Anthropic Messages API structures: `SDKAssistantMessage { type:'assistant', message: Message, parent_tool_use_id, uuid, session_id }` (:3405), `SDKUserMessage { type:'user', message: MessageParam, parent_tool_use_id, isSynthetic?, tool_use_result?, priority?, origin? }` (:5879). A non-empty `parent_tool_use_id` means the message belongs to a subagent.
- Harness-generated events: `system/init` (`SDKSystemMessage` :5580, containing model/tools/mcp_servers/permissionMode/slash_commands/output_style/skills/plugins/apiKeySource/capabilities), `result`, `stream_event`, `compact_boundary`, `api_retry`, the hook started/progress/response trio, the task_* family, `permission_denied`, `files_persisted`, `conversation_reset`, and so on.

- The `result` message: `SDKResultMessage = SDKResultSuccess | SDKResultError` (:5416). Key fields on success: `duration_ms / duration_api_ms / ttft_ms, num_turns, result, total_cost_usd, usage (main loop), modelUsage (per-model totals, including subagent/compaction auxiliary calls), permission_denials, structured_output, deferred_tool_use, result_index, queued_turn_count, session_id, uuid` (:5418-5481); error subtypes: `'error_during_execution' | 'error_max_turns' | 'error_max_budget_usd' | 'error_max_structured_output_retries'` (:5359).
- Tool-result encoding: besides the tool_result block, `SDKUserMessage.tool_use_result` carries a **structured per-tool Output object** ("the tool's full Output object, not the string content sent to the model"; for the Agent/Task tool the completed shape is the subagent's final report, :5884-5892).
- [docs] The headless documentation (https://code.claude.com/docs/en/headless) additionally specifies, on stream-json, `system/api_retry` (attempt/max_retries/retry_delay_ms/error_status/error enum), `system/plugin_install`, `hook_started/hook_progress/hook_response`, and `permission_denied`; `system/init.capabilities[]` is string-based capability negotiation (e.g. `interrupt_receipt_v1`, `interrupt_cancel_queued_v1`), and consumers are required to feature-detect rather than compare version numbers.

### 1.2 Session: continue / resume / fork / persistence

- `Options` [source: npm sdk.d.ts:1449-]: `continue?: boolean` (continue the most recent session in the current directory, :1522), `resume?: string` (by session id, :1991), `forkSession?: boolean` (used together with resume to produce a fork, :1637), `persistSession?: false` (in-memory-only session, :1745), `abortController` (cancellation, :1454), `cwd`.
- CLI flags [docs] (https://code.claude.com/docs/en/headless): `--continue`, `--resume <id|jsonl path>` (an absolute path to a transcript file can be passed directly), `--fork-session`.
- Persistence: the transcript lives at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` (non-alphanumeric characters in the cwd are replaced with `-`) [docs] (https://code.claude.com/docs/en/agent-sdk/sessions); resume across directories (v2.1.223+), and across hosts via `SessionStore` adapter mirroring (documentation page session-storage; `examples/session-stores/{s3,redis,postgres}` in the repo ship conformance tests) [source: repo examples].
- Session-management API (module-level functions): `listSessions()` (:1029), `getSessionMessages()` (:834), `getSessionInfo()` (:804), `renameSession()` (:3051), `tagSession()`, `deleteSession()` (:600), `forkSession({upToMessageId})` (:770); returns `SDKSessionInfo` (:5486). **Note: these are in-process functions of the SDK host (they read the transcript files directly), not control_request subtypes** — the only session-related control subtypes are the likes of `rename_session`.
- Interruption: `Query.interrupt(): Promise<SDKControlInterruptResponse | undefined>` [source: npm sdk.d.ts:2685], control subtype `interrupt` (:4348); a CLI that announces the `interrupt_receipt_v1` capability returns a receipt (a list of `still_queued` uuids, which must then be cancelled). Control-protocol retraction: `SDKControlCancelRequest {type:'control_cancel_request', request_id}` (:3677; semantics: retract one's own in-flight control_request, e.g. a can_use_tool question left behind after a turn was interrupted).
- Process-level cancellation: `abortController` + `endInput()`; SIGTERM semantics for `claude -p`: exit code 143, the current turn does not get a result written, the Bash process tree is killed, SessionEnd hooks run, and an unfinished turn is replayed on resume [docs: headless].

### 1.3 Agent loop, tools, and permissions

**Where the loop lives**: the agent loop runs entirely inside the closed-source CLI process; on the SDK side, `query()` is just a host loop that converts transport frames into an `AsyncGenerator<SDKMessage>` [source: npm sdk.d.ts:2671, `Query extends AsyncGenerator<SDKMessage, void>`]. The SDK host can register in-process tools (createSdkMcpServer, :543); the tools execute in the host, and the CLI calls back into them over the control protocol.

**The canUseTool approval callback** [source: npm sdk.d.ts:213-298]: `CanUseTool = (toolName, input, options) => Promise<PermissionResult | null>`. The options carry `signal / suggestions (PermissionUpdate[]) / blockedPath / mcpServer{name,source} / decisionReason / title / displayName / description / defaultToNo / suppressAlwaysAllowRule / toolUseID / agentID / requestId / matchedAskRule` — i.e. everything needed to render the UI is delivered by the protocol. Returns: `PermissionResult = {behavior:'allow', updatedInput?, updatedPermissions?} | {behavior:'deny', message, interrupt?: boolean}` (:2406). `allow{updatedInput}` lets the host **rewrite the tool's input arguments**. Underneath it is the `can_use_tool` control_request (SDKControlPermissionRequest), which supports out-of-band answers (e.g. writing back the request_id via a signed HTTP POST).

**Approval precedence** [docs] (https://code.claude.com/docs/en/agent-sdk/permissions): hooks → deny rules → ask rules → permission mode → allow rules → canUseTool; `AskUserQuestion`, MCP tools carrying `_meta["anthropic/requiresUserInteraction"]`, and rm on critical paths fall through to the callback even when an allow rule matches.

**Permission modes** [source: npm sdk.d.ts:2383]: `'default' | 'acceptEdits' | 'bypassPermissions' | 'plan' | 'dontAsk' | 'auto'` (auto = approval by a model classifier). Runtime switching: the `set_permission_mode` control_request (:4797) / `Query.setPermissionMode()` (:2692); there is also `setMcpPermissionModeOverride(server, 'default'|'auto'|null)` (can only tighten, :2709).

**Hooks** [source: npm sdk.d.ts:910]: `HookEvent` has 33 events: `'PreToolUse' | 'PostToolUse' | 'PostToolUseFailure' | 'PostToolBatch' | 'Notification' | 'UserPromptSubmit' | 'UserPromptExpansion' | 'SessionStart' | 'SessionEnd' | 'Stop' | 'StopFailure' | 'SubagentStart' | 'SubagentStop' | 'PreCompact' | 'PostCompact' | 'PreModelSwitch' | 'PostModelSwitch' | 'PermissionRequest' | 'PermissionDenied' | 'Setup' | 'TeammateIdle' | 'TaskCreated' | 'TaskCompleted' | 'Elicitation' | 'ElicitationResult' | 'ConfigChange' | 'WorktreeCreate' | 'WorktreeRemove' | 'InstructionsLoaded' | 'CwdChanged' | 'FileChanged' | 'DirectoryAdded' | 'MessageDisplay'`. Inside the SDK they are registered as in-process callbacks, `hooks?: Partial<Record<HookEvent, HookCallbackMatcher[]>>` (:1658), invoked via the `hook_callback` control_request; on the CLI side the event stream shows `SDKHookStartedMessage/Progress/Response`.

**Subagents**: the `agents` option holds the definitions (`AgentDefinition` :38, :1504), invoked via the Agent/Task tool; in the stream, subagent messages are attributed by `parent_tool_use_id` (null for the main session) [docs: headless "Follow subagent messages"]; by default only tool_use/tool_result are forwarded — text/thinking are forwarded only with `--forward-subagent-text`; token-level stream_event is not forwarded for subagents [docs: streaming-output]; nesting depth is reconstructed from the parent_tool_use_id chain. `supportedAgents()` can enumerate them.

**MCP**: `mcpServers` (stdio/SSE/HTTP/Sdk in-process) [source: npm sdk.d.ts:1149]; control subtypes include `mcp_status / mcp_call / mcp_set_servers / mcp_reconnect / mcp_toggle / mcp_message`; `system/init` reports `mcp_servers[].status` and `mcp_server_errors` [docs: headless]; `mcpServerStatus()` queries status (:2841).

**Parallel tool calls**: a single assistant message carries multiple tool_use blocks; approvals happen one by one keyed by `toolUseID` ("Multiple tool calls in the same assistant message will have different toolUseIDs", :274-277); the `PostToolBatch` hook (:910) and changelog 0.3.274 "queued background-task completions to share one model call" corroborate that batching exists. A dedicated parallelism-control parameter: not found in the source.

### 1.4 Streaming (partial messages / stream_event)

- The option `includePartialMessages?: boolean` [source: npm sdk.d.ts:1790] produces `SDKPartialAssistantMessage { type:'stream_event', event: BetaRawMessageStreamEvent, parent_tool_use_id: string|null, uuid, session_id, ttft_ms?, user_message_uuid?, user_message_uuids?, resume_reason? }` (:5170). `event` is a **native Anthropic Messages API stream event** (message_start / content_block_start / content_block_delta / content_block_stop / message_delta / message_stop); the SDK does no accumulation.
- Event ordering [docs] (https://code.claude.com/docs/en/agent-sdk/streaming-output): as soon as each non-empty content block completes, an AssistantMessage is emitted (same message id), followed by `content_block_stop`; a ResultMessage comes last. Structured output appears only in the final result and is not streamed.
- Limitations: stream_event is emitted only for the main session (token-level deltas of subagents are not forwarded); `user_message_uuid` binds a reply frame to the uuid of the user message that triggered it (frame-binding semantics — directly useful as a reference for ARI's request↔event correlation).
- On the CLI side: `claude -p --output-format stream-json --verbose --include-partial-messages`, JSON Lines on stdout, with the result as the last line [docs: headless]; when stdout is consumed slowly, it drains before exit, capped at 30s (v2.1.214+).
- Thinking: a dedicated `SDKThinkingTokensMessage`; the `set_max_thinking_tokens` control subtype supports `thinking_display: 'summarized'|'omitted'|'highlights'` [source: npm sdk.d.ts:4774].

### 1.5 Context management (compaction)

- Boundary message: `SDKCompactBoundaryMessage { type:'system', subtype:'compact_boundary', compact_metadata: { trigger: 'manual'|'auto', pre_tokens, post_tokens?, duration_ms?, preserved_segment?/preserved_messages? (uuid anchors of preserved messages, so resume can re-link) } }` [source: npm sdk.d.ts:3530-3560] — **client-visible compaction is a first-class event, carrying the before/after token values and the trigger kind**.
- Triggers: automatic + manual via `/compact`; pre/post hooks `PreCompact`/`PostCompact` (:910); compaction counts toward `modelUsage` as an internal model call [source: sdk.d.ts:5460].
- Context-usage query: `Query.getContextUsage({detail:'summary'|'full'})`, control subtype `get_context_usage`, returns tokens broken down by system prompt/tools/messages/MCP/memory (:2852).

### 1.6 Transport and the control protocol (control_request/control_response)

- **Same-channel multiplexing**: data messages and control messages run over the same JSON Lines stdin/stdout. The wire-level union: `StdoutMessage = SDKMessage | SDKActiveGoalMessage | SDKControlResponse | SDKControlRequest | SDKControlCancelRequest | SDKKeepAliveMessage` [source: npm sdk.d.ts:9049] (KeepAlive is a heartbeat frame).
- Control envelope: `SDKControlRequest { type:'control_request', request_id (chosen by the sender, echoed in the response), request: SDKControlRequestInner }` (:4688); response `SDKControlResponse { type:'control_response', response: ControlResponse | ControlErrorResponse }` (:4739), with the error form carrying `request_id`. Retraction: `control_cancel_request` (:3677).
- `SDKControlRequestInner` has 37 subtypes (:4699): `interrupt / can_use_tool (permissions) / initialize / set_permission_mode / set_model / set_max_thinking_tokens / rename_session / set_color / mcp_status / get_context_usage / get_session_cost / list_models / get_usage / get_binary_version / mcp_call / file_suggestions / hook_callback / mcp_message / rewind_files / cancel_async_message / read_file / seed_read_state / mcp_set_servers / register_repo_root / reload_plugins / reload_skills / reload_output_styles / mcp_reconnect / mcp_toggle / stop_task / background_tasks / apply_flag_settings / get_settings / get_hooks_listing / update_settings / elicitation / request_user_dialog / list_permission_rules`. The `initialize` response carries `pending_permission_requests[]`/`pending_user_dialog_requests[]` (a client joining mid-session can re-arm in-flight questions, :317-331); `reinitialize()` is for replay after a transport reconnect.
- Transport abstraction: `interface Transport { write / readMessages(): AsyncGenerator<StdoutMessage> / close / isReady / endInput / expectControlResponse? / markDelivered? / waitForExit? / Symbol.dispose? }`; a comment states outright "support both process and WebSocket transports" [source: npm sdk.d.ts:9258-9314]. The default `ProcessTransport` spawns the CLI as a child process; the bundle confirms the existence of `DirectConnectTransport`, `kWebSocket`, and `fromSSEResponse` [closed-source, bundle-inspected: sdk.mjs]; there are also a `/browser` endpoint (SSE; types in browser-sdk.d.ts) and a `/bridge` endpoint (CCR worker: a per-session handle + JWT, `SessionState = 'idle'|'running'|'requires_action'`) [source: npm bridge.d.ts].

### 1.8 File-change reporting and background-task notes

- **File changes**: not watcher-based. There are three structured routes: (1) the `tool_use_result` structured object on the tool result (carried on the user message, per-tool Output); (2) the `rewind_files` control_request (user_message_id + dry_run) + file checkpointing [source: npm sdk.d.ts:4750; docs: /agent-sdk/file-checkpointing]; (3) the hook events `FileChanged/CwdChanged/DirectoryAdded` (:910). A generic "workspace diff push" event: not found in the source.
- **Background tasks**: a first-class runtime event family `SDKTaskStartedMessage / SDKTaskProgressMessage / SDKTaskUpdatedMessage / SDKTaskNotificationMessage / SDKBackgroundTasksChangedMessage`; notifications can carry `origin.kind='task-notification'` (replayed into user messages) and `reason:'worker_restart'` [source: npm sdk.d.ts:5025; CHANGELOG 0.3.269/0.3.274]; the control plane has the `stop_task / background_tasks` control subtypes [source: sdk.d.ts:4809]. Changelog 0.3.274 records "queued background-task completions to share one model call, each still producing its own result" — the protocol semantics of merging background completions into the main loop. [docs: headless] adds: in `claude -p`, backgrounded bash is terminated ~5s after the result is returned and stdin closes; background subagents/workflows are instead waited on to completion (default 10-minute ceiling, adjustable via `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`); a Monitor tool's watch is waited on and keeps reporting.

## 2. Gemini CLI (google-gemini/gemini-cli)

### 2.1 Message model: Turn / TurnEvent

- The core event stream is the `ServerGeminiStreamEvent` union type, with the event-type enum `GeminiEventType` [source: gemini-cli/packages/core/src/core/turn.ts:55-74]: `Content / ToolCallRequest / ToolCallResponse / ToolCallConfirmation / UserCancelled / Error / ChatCompressed / Thought / MaxSessionTurns / Finished / LoopDetected / Citation / Retry / ContextWindowWillOverflow / InvalidStream / ModelInfo / AgentExecutionStopped / AgentExecutionBlocked`. Each kind has a named `ServerGemini*Event` type (:76-246), e.g. `ServerGeminiContentEvent{value:string}`, `ServerGeminiToolCallRequestEvent{value:ToolCallRequestInfo}`, `ServerGeminiFinishedEvent{value:{reason, usageMetadata}}`.
- Distinguishing model stream from runtime: `Content/Thought/Citation/Retry` come straight off the model stream; `ToolCall*/ChatCompressed/MaxSessionTurns/LoopDetected/InvalidStream` (where `ContextWindowWillOverflow` carries estimated/remaining token counts, :98-104) are harness runtime events.
- The headless wire model (the counterpart of Claude's stream-json): `--output-format text|json|stream-json` [source: packages/core/src/output/types.ts:9-13, `OutputFormat`]; the streamed-event enum `JsonStreamEventType = init | message | tool_use | tool_result | error | result` (:30-37), with shapes: `InitEvent{session_id, model}`, `MessageEvent{role:'user'|'assistant', content, delta?}`, `ToolUseEvent{tool_name, tool_id, parameters}`, `ToolResultEvent{tool_id, status:'success'|'error', output?, error?}`, `ErrorEvent{severity, message}`, `ResultEvent{status, stats: StreamStats{total/input/output/cached_tokens, duration_ms, tool_calls, models}}` (:44-109); `JsonOutput{session_id, response, stats, error, warnings}` for json mode (:21-27). Formatters: `packages/core/src/output/stream-json-formatter.ts`, `json-formatter.ts`; assembly: `packages/cli/src/nonInteractiveCli.ts:255-596`.
- Comparison: Gemini's runtime event surface (~18 kinds) is far smaller than Claude's (~38); it lacks glue events such as hook stream events, task notifications, and session state; UI-specific semantics (Thought is normalized into a `{subject, description}` ThoughtSummary) are produced uniformly by core.

### 2.2 Session and the chat service

- Persistence: `chatRecordingService` writes sessions to disk; `sessionSummaryService` produces summaries [source: packages/core/src/services/chatRecordingService.ts, sessionSummaryService.ts].
- Resume: CLI flags `--resume latest|<index>` ("Resume a previous session. Use \"latest\" for most recent or index number"), `--session-id`, `--session-file`; the three are mutually exclusive [source: packages/cli/src/config/config.ts:97,243-249,401-410].
- Fork: **not found in the source** (grepping `forkSession|fork_session` across the whole repo yields nothing) — the missing fork semantics are a notable gap between Gemini CLI and Claude Code.
- SDK package: `GeminiCliAgent.session()` / `resumeSession(id)` [source: packages/sdk/SDK_DESIGN.md, src/agent.ts]; on the ACP surface, `newSession` / `loadSession` [source: packages/cli/src/acp/acpSessionManager.ts (as listed in the README)].
- Cancellation: an `AbortSignal` runs throughout (`sendStream(prompt, signal)`, SDK session.ts:211); interactive mode has the `UserCancelled` event; non-interactive mode has no interrupt control subtype (not found in the source).

### 2.3 Agent loop and CoreToolScheduler (approval, parallel tools)

- Loop: the Turn class in `packages/core/src/core/turn.ts` iterates the model stream and yields events; `GeminiClient.sendMessageStream` (`core/client.ts`) drives the turn loop and auto-compaction.
- Scheduler: the `Scheduler` class at `packages/core/src/scheduler/scheduler.ts:99`; the tool-call state machine `CoreToolCallStatus = validating | scheduled | error | success | executing | cancelled | awaiting_approval` [source: scheduler/types.ts:26-34]; the `ToolCall` union: Validating/Scheduled/Errored/Successful/Executing/Cancelled/Waiting (:189-196). `WaitingToolCall{status:'awaiting_approval', confirmationDetails: ToolCallConfirmationDetails | SerializableConfirmationDetails, correlationId?}` (:164-185) — the confirmation payload is migrating toward being **serializable** (a TODO comment states outright that the callback-carrying old shape will be removed); this is key evidence for a cross-process approval protocol.
- Seven kinds of confirmation details [source: packages/core/src/tools/tools.ts:1094-1101]: `sandbox_expansion / edit / exec / mcp / info / ask_user / exit_plan_mode` (e.g. `ToolExecuteConfirmationDetails{title, command, rootCommand, rootCommands[], untrustedFlags?, modifiedBuildFiles?}`, :1037-1048).
- The approval-outcome enum `ToolConfirmationOutcome = proceed_once | proceed_always | proceed_always_and_save | proceed_always_server | proceed_always_tool | modify_with_editor | cancel` [source: tools/tools.ts:1106-1114] — finer-grained than Claude's allow/deny binary (persistence level and editor-based parameter edits are both outcomes).
- Approval modes: `ApprovalMode = DEFAULT | AUTO_EDIT('autoEdit') | YOLO | PLAN` [source: packages/core/src/policy/types.ts:48-53]; each tool call records its `approvalMode` [source: scheduler/types.ts:89]; the policy engine lives in `packages/core/src/policy/`.
- Parallelism: the scheduler supports concurrent execution with completion callbacks (`AllToolCallsCompleteHandler`, `ToolCallsUpdateHandler` [source: scheduler/types.ts:207-216]); dedicated tests exist, such as `scheduler_parallel.test.ts` and `scheduler_waiting_callback.test.ts` [source: the scheduler/ directory].
- Hook system: `HookEventName = BeforeTool | AfterTool | BeforeAgent | AfterAgent | Notification | SessionStart | SessionEnd | PreCompress | BeforeModel | AfterModel | BeforeToolSelection` (11) [source: packages/core/src/hooks/types.ts:43-55], with a full registry/planner/runner/aggregator layering; of Claude's 33 hook events, filesystem-observation kinds such as FilesChanged/CwdChanged/TaskCreated are not found in Gemini's source.
- Subagents: `packages/core/src/agents/` (agent-scheduler, local-invocation, remote-session-invocation (A2A), browser agent); `AgentTerminateMode = ERROR|TIMEOUT|GOAL|MAX_TURNS|ABORTED|ERROR_NO_COMPLETE_TASK_CALL`, `OutputObject{result, terminate_reason, turn_count?, duration_ms?}` [source: agents/types.ts:18-42]; the tool surface includes `complete-task` and `activate-skill` [source: the tools/ directory].
- MCP: `tools/mcp-client.ts`, `mcp-tool.ts`, `mcp-client-manager.ts`, `list-mcp-resources.ts` [source: the tools/ directory].
- Tool-result encoding: `ToolCallResponseInfo{callId, responseParts: Part[], resultDisplay?: ToolResultDisplay, error?, errorType?, outputFile?, contentLength?, data?}` [source: scheduler/types.ts:59-73] — the split between `resultDisplay` (for the UI) and `responseParts` (for the model) is the key design of its structured results.

### 2.4 Streaming events

- Model-stream granularity: `Content` events are chunk-wise text deltas, and `Thought` carries a `ThoughtSummary` (subject/description) [source: core/turn.ts:147-157]; there is **no** mode that passes through native Gemini API stream events (no counterpart of Claude's stream_event); raw event pass-through: not found in the source.
- The stream granularity of the stream-json output is flagged by `MessageEvent.delta?: boolean` [source: output/types.ts:50-55]; tools appear as paired `tool_use`/`tool_result` events; `ResultEvent.stats` is the final summary.
- ACP-surface streaming: `sessionUpdate` notifications include `agent_message_chunk / agent_thought_chunk / tool_call / tool_call_update / user_message_chunk / available_commands_update` [source: packages/cli/src/acp/acpSession.ts:181,231,248,258,267,295,425-434,809].

### 2.5 Context management: the compression service

- `ChatCompressionService.compress(chat, promptId, force, model, config, hasFailedCompressionAttempt, signal)` [source: packages/core/src/context/chatCompressionService.ts:239-]; the default threshold `DEFAULT_COMPRESSION_TOKEN_THRESHOLD = 0.5` (as a fraction of the model's token limit, :41), overridable via `config.getCompressionThreshold()` (:272-274); before compressing, the history is truncated to a token budget (`truncateHistoryToBudget`); the result is `ChatCompressionInfo{originalTokenCount, newTokenCount, compressionStatus}`.
- The status enum `CompressionStatus = COMPRESSED | COMPRESSION_FAILED_INFLATED_TOKEN_COUNT | COMPRESSION_FAILED_TOKEN_COUNT_ERROR | COMPRESSION_FAILED_EMPTY_SUMMARY | NOOP | CONTENT_TRUNCATED` [source: core/turn.ts:183-207] — failure causes are observable at fine grain (inflation / count error / empty summary / truncated degradation).

### 2.6 Transport: local REPL, IDE mode, ACP adapter, server/SDK

- Local REPL: the core event stream connects in-process directly to the Ink/React UI, with no wire protocol; non-interactive runs use `--output-format json/stream-json` (see 2.1).
- **ACP adapter (important)**: `packages/cli/src/acp/` implements Zed's Agent Client Protocol: `acpStdioTransport.ts` uses `acp.ndJsonStream(stdout, stdin)` + `new acp.AgentSideConnection(...)` to set up **ndjson JSON-RPC over stdio** [source: acpStdioTransport.ts:25-26; README]; `acpRpcDispatcher.ts` (the GeminiAgent class, the JSON-RPC entry point), `acpSessionManager.ts` (newSession/loadSession/multiple sessions), `acpSession.ts` (prompt execution, @file resolution, tool execution, slash-command interception, streaming pass-back), `acpFileSystemService.ts` (fs access within the workspace boundary), `acpErrors.ts` (error-code mapping).

- IDE mode: `packages/core/src/ide/` (ide-client; the `IdeContextStore`/`ideContextStore` singleton, where the IDE pushes open-files/selection context; detect-ide; ide-installer) + the `packages/vscode-ide-companion` extension [source: the ide/ directory].
- Server/SDK: `packages/a2a-server` (an A2A protocol server, self-described as experimental in its README), `packages/sdk` (`@google/gemini-cli-sdk`, the in-process `GeminiCliAgent` whose `sendStream` yields `ServerGeminiStreamEvent`; SDK_DESIGN.md self-reports that hooks/skills/subagents/ACP are still missing) [source: packages/a2a-server/README.md, packages/sdk/SDK_DESIGN.md, src/session.ts:211-265].

### 2.8 File-change reporting and background-task notes

- **File-change reporting**: primarily "tool self-reporting" — the Edit/Write tools' `resultDisplay` carries a structured diff (`FileDiff`, `diffStat.model_added_lines/model_removed_lines`, computed with the `diff` library) [source: packages/core/src/tools/edit.ts:41-69,442-444; diffOptions.ts]; at confirmation time `ToolEditConfirmationDetails` already provides a diff preview; ACP delivers `invocation.toolLocations()` as `toolCall.locations` [source: acpSession.ts:775]. On the git side there is `gitService.ts` (repository state). No filesystem-watcher broadcast events (not found in the source).
- **Background tasks**: the shell tool has an `is_background` parameter; the command is wrapped in a subshell to capture the background PID, and background tasks do not block streaming output [source: packages/core/src/tools/shell.ts:97,119,160-163,617-631]; `ExecutionLifecycleService` centrally broadcasts execution events (including per-pid) [source: services/executionLifecycleService.ts:34-53]. Compared with Claude's task_started/task_notification event family, what is missing is a protocolized "background task completed → inject into next-turn context" notification (not found in the source).

## 3. Implications for ARI design (summary)

1. **Control channel and data channel multiplexed over one stream, with request_id correlation** is the common convergence point of both implementations: Claude's `control_request`/`control_response`/`cancel_request` (37 subtypes) run inside stdout JSON Lines; Gemini's ACP uses ndjson JSON-RPC. ARI's control sub-protocol has mature precedents to tailor.
2. **Approval messages must carry all the metadata the UI needs**: Claude's `can_use_tool` options (title/displayName/description/suggestions/blockedPath/decisionReason) plus `PermissionResult.allow.updatedInput` to rewrite the input arguments; Gemini's migration to serializable `SerializableConfirmationDetails` and its 7-value outcome. ARI should support at least allow/deny/allow-with-edited-input + persistence suggestions.
3. **Reply↔request binding**: Claude uses `user_message_uuid` to bind stream frames back to the message that triggered them, and `parent_tool_use_id` to hang subagent frames onto the tree. ARI needs equivalent correlation fields; otherwise a UI with multiple concurrent subagents/turns cannot reconstruct attribution.
4. **Compaction is a first-class event**: Claude's `compact_boundary` (trigger/pre_tokens/preserved_messages), Gemini's `ChatCompressed` (before/after token counts + a fine-grained failure enum). ARI's compaction event should carry the trigger kind, token accounting, and summary anchors together.
5. **Dual channels for tool results**: Gemini splits `responseParts` (for the model) from `resultDisplay` (for the UI); Claude splits the tool_result text from the `tool_use_result` structured object. ARI should explicitly distinguish model-facing from client-facing payloads.
6. **Capability negotiation**: Claude's `system/init.capabilities[]` string set + the "ignore unknown" rule is lighter than version comparison and can be adopted directly as the ARI handshake.
7. **Gap items**: fork (absent in Gemini), interrupt receipt (absent in Gemini), the background-task notification event family (absent in Gemini), and a unified file-change event stream (both implementations rely primarily on tool self-reporting; if ARI provides watcher events it goes beyond both existing surfaces).
