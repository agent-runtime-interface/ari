## 0. 总体架构：三层分离

Pi 的分层是 ARI 最直接的先验：

1. **`packages/ai`（模型 API 层）**：统一多 provider 的流式 LLM API 与消息类型（`AssistantMessage`、`ToolCall`、thinking block、`AssistantMessageEvent`）。不认识"agent"。
2. **`packages/agent`（agent 运行时层）**：`Agent` 类 + 低层 `agentLoop` + 事件流（`AgentEvent`）。通过 `StreamFn` 注入模型调用（`packages/agent/src/types.ts:33-37` 的 `StreamFn` 类型，注释明确 "The loop passes a normalized transcript ... never by `context.systemPrompt`"），provider 无关；`packages/agent/src/stream-fn.ts:1-20` 提供 `setDefaultStreamFn` 兜底注入（`packages/coding-agent/src/core/sdk.ts:45` 调用 `setDefaultStreamFn(streamSimple)`）。
3. **`packages/coding-agent`（产品层）**：CLI、TUI、session 持久化、内置 tools、extensions、RPC/print/json 模式、compaction、retry。

一个重要的"进行中"事实：`packages/agent/src/harness/`（`agent-harness.ts`、`runtime/`、`session/`、`pico3/`）是一套**durable runtime**（AgentHarness），`packages/agent/docs/harness.md` 为规范文档，§0.9（约 L141 起）声明 WP00–WP07 已实现、其余（如 `watchSession` R12、schema 迁移 R11、C1 remote transport）未实现。下文以 shipping 的 `Agent`+`AgentSession` 为主线，durable harness 作为演进方向单列。

## 1. Session：创建、resume、ID、持久化、多客户端、中断、fork、崩溃恢复

**创建与 ID**【source】
- `SessionManager.newSession()`（`packages/coding-agent/src/core/session-manager.ts:1057-1083`）：生成 `sessionId = createSessionId()`（`uuidv7()`，L264-266），写 `SessionHeader{type:"session", version:CURRENT_SESSION_VERSION(=3), id, timestamp, cwd, parentSession?}`（L43-50、L1063-1070）。文件名 `<ISO timestamp 替换 :. 为 ->_<sessionId>.jsonl`（L1078-1081）。
- `--session-id` 自定义 ID 需过 `assertValidSessionId` 正则（L268-274）。entry id 为 8 位 hex（`generateId`，L277-284）。

**持久化格式与位置**【source】【docs】
- JSONL，append-only 树结构：每条 `SessionEntryBase{type, id, parentId: string|null, timestamp}`（L57-62）。`FileEntry = SessionHeader | SessionEntry`（L197）。**【docs】** `packages/coding-agent/docs/session-format.md`（L1-10 附近）：`~/.pi/agent/sessions/--<path>--/<timestamp>_<session-id>.jsonl`；v1 线性→v2 树→v3 重命名 hookMessage 为 custom，载入时自动迁移（`migrateToCurrentVersion`，session-manager.ts L1092）。
- 目录由 cwd 编码而来：`getDefaultSessionDirPath` 把 cwd 前导 `/` 去掉、`/\:` 换 `-`，包成 `--...--`（L589-592）；agent dir 为 `~/.pi/agent`（`packages/coding-agent/src/config.ts:528-531`，env `PI_CODING_AGENT_DIR` 可覆盖，L508）。sessions dir：`config.ts:572-574`。
- 延迟落盘契约：**首条 assistant message 出现前不写文件**（`_persist`，L1160-1187：`hasAssistant` 为 false 且未 flushed 时挂起；首次 flush 用 `openSync(..., "wx")` 独占创建并全量写入，之后逐条 `appendFileSync`）。空文件/损坏行容错：`loadEntriesFromFile` 跳过无法 JSON.parse 的行（L616-624），文件尾补 `\n`（L668）。
- **无独立"leaf 指针文件"**：leaf 即"文件中最后一条 entry"（`_buildIndex`：遍历 fileEntries，`this.leafId = entry.id`，L1103-1122）。树上任意 entry 的 `parentId` 才是分支事实来源。

**Resume**【source】
- CLI flags：`--continue|-c`（继续最近会话）、`--resume|-r`（选择器）、`--session <path|id>`、`--session-id`、`--fork <id>`、`--session-dir`（`packages/coding-agent/src/cli/args.ts:20-30,110-141,293-297`）。
- `findMostRecentSession(sessionDir, cwd)`：按 mtime 排序 .jsonl，读首行 header 校验 `cwd` 匹配（L749-768，`readSessionHeader` 有 1MB 扫描上限 L607、L685-727）。

**中断（ESC abort）**【source】
- 交互模式：`defaultEditor.onEscape`（`packages/coding-agent/src/modes/interactive/interactive-mode.ts:2965-2996`）：isStreaming 时 `restoreQueuedMessagesToEditor({ abort: true })` —— **abort 同时把队列中 steering/follow-up 消息还回编辑器**；isBashRunning 时 `abortBash()`；空编辑器双击 ESC（<500ms，L2979）按设置打开 `/tree` 或用户消息选择器（分支导航）。键位注册：`app.interrupt: "escape"`（`packages/coding-agent/src/core/keybindings.ts:93`）。
- 运行时侧：`AgentSession.abort()`（`packages/coding-agent/src/core/agent-session.ts:2075-2082`）= abort retry + compaction + branch summary + `agent.abort()`（`AbortController.abort()`，`packages/agent/src/agent.ts:338-340`）+ `waitForIdle()`。RPC 侧对应 `abort` 命令（rpc-types.ts L25）。

**Fork / branch（会话树）**【source】
- **分支**（同文件）：`branch(branchFromId)` 只移动 leaf 指针（L1572-1577），后续 append 生成新子链；`resetLeaf()`（L1584-1586）允许重新编辑首条用户消息（新根）；`branchWithSummary(fromId, summary, ...)` 追加 `BranchSummaryEntry{fromId, summary, usage?, fromHook?}` 记录被放弃路径（L1593-1618；类型 L106-116）。
- **fork**（新文件）：`createBranchedSession(leafId)` 复制 root→leaf 路径到新 session 文件，header 带 `parentSession: 旧文件路径`（L1625-1724）。CLI `--fork`、RPC `fork`/`clone` 命令、extension `ctx.fork()`（extensions/types.ts L373-377）。`navigateTree(targetId, {summarize,...})` 切换树节点时可生成 LLM 摘要（agent-session.ts L3581）。
- 【docs】`docs/session-format.md` Tree Structure 节给出树状图与 "leaf 是当前位置" 定义。

**崩溃恢复**【source】
- 三个机制：(1) append-only + 损坏行跳过（L616-624）；(2) 首条 assistant 前不建文件，避免空/半初始化文件；(3) 崩溃记录 `crashes.json`（`packages/coding-agent/src/core/crash-log.ts:19-32`，`{timestamp, version, kind: "uncaught_exception"|"fatal_error", message, stack, sessionFile, cwd}`，最多 5 条 7 天）。durable harness（harness/docs）则显式做 operation 级恢复（effect_pending 状态机），但按 §0.9 部分未上产品。

**多客户端**【source】
- Shipping 的 RPC 模式是**单 stdin/stdout、单客户端**子进程模型（`docs/rpc.md`："Pi as a long-lived subprocess controlled through JSON records on stdin and stdout"）。
- 实验栈支持多客户端：`packages/server/src/session-router.ts:32-42`（`HostedSession{id, handle, attachments: Set<ClientAttachment>}`，一个 session 多个 attachment/客户端），协议层 `packages/protocol/README.md`（PROTOCOL_VERSION 8，`{serverId, sessionId, attachmentId}` 路由、attach/detach）。另 `packages/coding-agent/src/experimental/session-worker-manager.ts`（session worker 进程池 + chord 服务）。

## 2. Message 模型：三层类型体系（ARI 核心先验）

### 2.1 模型 API 消息（packages/ai）

`Message = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage`（`packages/ai/src/types.ts:553`）。

- `SystemMessage`（L491-507）：`content` + **`sections?: Record<string, string|null>`**（命名 prompt section，null 删除）+ **`toolsAdded?: Tool[]` / `toolsRemoved?: ToolReference[]`**。注释：**transcript 的系统消息承载 prompt 与工具声明；回放全部系统消息即得当前 prompt/tools** —— 增量式、可回放的 loadout 协议（ARI 应重点吸收）。
- `UserMessage`（L509-513）：`content: string | (TextContent|ImageContent)[]` + timestamp。
- `AssistantMessage`（L515-537）：`content: (TextContent | ThinkingContent | ToolCall)[]`；`api/provider/model/responseModel?/responseId?`；`providerThinkingLevel?`；`diagnostics?`；`usage: Usage`；`stopReason: StopReason`；`deferred?: DeferredHandle`（延迟响应轮询句柄，L469-479）；`errorMessage?/rawStopReason?/endTurn?`。
- `ToolResultMessage`（L539-551）：`toolCallId, toolName, content: (TextContent|ImageContent)[], details?, usage?, isError, timestamp`。
- Content blocks：`TextContent{type:"text", text, textSignature?}`（L364-368）、`ThinkingContent{type:"thinking", thinking, thinkingSignature?, redacted?}`（L370-378，redacted thinking 的加密负载存 signature 供回传）、`ImageContent{type:"image", data(base64), mimeType}`（L380-384）、`ToolCall{type:"toolCall", id, name, arguments: JsonObject, thoughtSignature?, namespace?}`（L386-394）。
- `StopReason = "pending"|"stop"|"length"|"toolUse"|"error"|"aborted"|"deferred"`（L419）。`Usage`（L396-417）：input/output/cacheRead/cacheWrite/cacheWrite1h?/**reasoning?**/totalTokens/cost{...}。
- `Tool`（L600-605）：`{name, description, parameters(TypeBox TSchema), constrainedSampling?}`。

### 2.2 AgentMessage（运行时消息，可扩展）

`AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]`（`packages/agent/src/types.ts:370`），通过 declaration merging 扩展（L361-363 注释）。coding-agent 注册了 4 种（`packages/coding-agent/src/core/messages.ts:71-76`）：`bashExecution`（L29-40：command/output/exitCode/cancelled/truncated/fullOutputPath/excludeFromContext）、`custom`（L47-54：customType/content/display/details）、`branchSummary`（L57-61）、`compactionSummary`（L66-70）。`convertToLlm()`（L149-185）把它们映射成 user message（或按 `excludeFromContext` 丢弃）；`Agent` 默认 `defaultConvertToLlm` 只放行四种标准 role（`packages/agent/src/agent.ts:38-46`）。

### 2.3 运行时事件（packages/agent `AgentEvent`）—— ARI 事件词汇的先验

`packages/agent/src/types.ts:485-500`，**共 10 种**：
- 生命周期：`agent_start`、`agent_end{messages}`；
- Turn：`turn_start`、`turn_end{message, toolResults}`（注释：一个 turn = 一次 assistant 响应 + 其 tool calls/results）；
- Message：`message_start{message}`、`message_update{message, assistantMessageEvent}`（仅 assistant 流式期间）、`message_end{message}`；
- Tool：`tool_execution_start{toolCallId, toolName, args}`、`tool_execution_update{..., partialResult}`、`tool_execution_end{..., result, isError}`。

### 2.4 会话级事件（coding-agent `AgentSessionEvent`）

`packages/coding-agent/src/core/agent-session.ts:164-205`：`AgentEvent` 全集（`agent_end` 增加 `willRetry`）+ `agent_settled`（"Pi 不再自动续跑"）+ `queue_update{steering, followUp}` + `compaction_start/end{reason: manual|threshold|overflow}` + `entry_appended{entry}` + `session_info_changed{name}` + `thinking_level_changed{level}` + `auto_retry_start/end` + `summarization_retry_*` + `bash_execution_update{id?, delta}`（RPC 用户 bash 输出）。

### 2.5 Session 持久化 entry（11 种 + header）

`session-manager.ts:183-194`：`SessionMessageEntry`、`ThinkingLevelChangeEntry`、`ModelChangeEntry`、`UsageEntry`（kind/provider/model/usage/note，L80-89）、`CompactionEntry`（summary/firstKeptEntryId/tokensBefore/details/usage/fromHook/**systemMessage 完整 checkpoint**，L91-104）、`BranchSummaryEntry`（L106-116）、`CustomEntry`（不入 LLM 上下文）、`CustomMessageEntry`（**入** LLM 上下文，display 控制 TUI，L159-165）、`ContextEditEntry`（append-only 地改写早前 entry 的模型可见内容或置 null 省略，L175-180）、`LabelEntry`、`SessionInfoEntry`。

## 3. Agent Loop

**入口与结构**【source】
- `agentLoop(prompts, context, config, signal, streamFn)` / `agentLoopContinue(...)`（`packages/agent/src/agent-loop.ts:37-99`）返回 `EventStream<AgentEvent, AgentMessage[]>`；`runLoop`（L162-320）为双循环：
  - **内层** `while (hasMoreToolCalls || pendingMessages.length > 0)`：依次 `prepareNextTurn`（可换 context/model/thinkingLevel，L184-207）→ 追加 prepared/steering 消息 → `prepareRequest`（L218-238）→ `streamAssistantResponse` → 若 `stopReason` 为 error/aborted 直接收尾（L244-255）→ 收集 toolCall blocks → 执行工具 → `finishTurn`（可 `{action:"continue"|"end"}`）→ `turn_end`。
  - **外层**：agent 本应停止时拉 `getFollowUpMessages()`（L301-307），有则续跑；否则若 `finishTurn` 给了 `explicitContinuation`，仅补一轮 context-only 请求（L309-313）；否则退出发 `agent_end`。
- **stopReason==="length" 的处理**：token 截断的 assistant 消息中所有 tool call 一律判失败（`failToolCallsFromTruncatedMessage`，L475-500，错误文案明确要求模型重新发起），防止执行参数被静默截断的调用。细节注释（L468-474）指出流式参数经"JSON salvage parser"补全，可能解析成功但语义不完整 —— 这条经验对 ARI 有直接价值。

**Steering / followUp（排队注入）**【source】
- `Agent.steer(message)` / `followUp(message)`（`packages/agent/src/agent.ts:296-303`）；两个 `PendingMessageQueue`，`QueueMode = "all" | "one-at-a-time"`（types.ts L55），默认 `one-at-a-time`（agent.ts L244-245）；`steeringMode`/`followUpMode` setter（L278-293）。语义：steering 在当前 assistant turn 的工具执行完成后、下一请求前注入（"Tool calls from the current assistant message are not skipped"，types.ts L279-289）；followUp 在 agent 本应停止时注入（L291-302）。`prepareNextTurn` 耗时（如 compaction）期间会再次轮询 steering（agent-loop.ts L200-205），但 one-at-a-time 模式下只在首轮空轮询时补拉，避免一次注入两条（L203-205 注释）。
- RPC 侧：`prompt` 命令带 `streamingBehavior: "steer"|"followUp"`，另有独立 `steer`/`follow_up`/`clear_queue` 命令（rpc-types.ts L22-26, L43-44）。

**并行工具执行**【source】
- `ToolExecutionMode = "sequential" | "parallel"`（types.ts L47），`AgentLoopConfig.toolExecution` 默认 **parallel**（agent.ts L250）；**per-tool 覆盖**：`AgentTool.executionMode`（types.ts L461-467），只要 batch 内有一个 sequential 工具即整批顺序执行（agent-loop.ts L512-519）。
- 并行实现（L583-657）：准备/校验/beforeToolCall 顺序做，执行并发；`tool_execution_end` 按**完成顺序**发，tool-result 消息按**assistant 源顺序**发（types.ts L39-46 注释明确该顺序契约）。**批量终止规则**：所有 result.terminate===true 才提前终止（`shouldTerminateToolBatch`，L685-687）。

**Abort**【source】
- 每次 run 一个 `AbortController`（`ActiveRun`，agent.ts L175-179、L503-526）；`agent.abort()` 中止；顺序执行时每个 tool call 后检查 `signal?.aborted` 跳出（agent-loop.ts L572-574）；并行场景下未开始的调用直接返回 aborted 错误结果（L617-625）。工具内部负责响应 signal（如 bash `killProcessTree`，见 §7）。abort 后循环以 stopReason "aborted" 收尾（L244-255）。

**失败/重试**【source】
- 工具执行 throw → `createErrorToolResult`（L863-868）→ `isError: true` 的 toolResult 消息（L880-893），**无工具级自动重试**；assistant 错误的重试在产品层：`AgentSession._prepareRetry`（agent-session.ts L3380-3406，默认 maxRetries=3、baseDelayMs=2000 指数退避，settings-manager.ts L932-937），可重试判定 `isRetryableAssistantError`，**context overflow 不可重试、走 compaction 恢复**（L3324-3330）。事件：`auto_retry_start/end`。
- **max iterations / loop detection / 预算上限：源码中未找到**（grep `maxTurns|maxIterations|loop detection` 无果）。循环终止完全依赖模型停止 + `finishTurn` 钩子 + 队列空。【docs】extensions.md "Guard continuation conditions because an unconditional continuation can loop" 也确认无硬护栏。

**其他钩子**：`transformContext`（上下文窗口管理，types.ts L221-240）、`getApiKey`（长任务中刷新 OAuth token，L242-250）、`beforeToolCall`（可 block/terminate，L315-322）、`afterToolCall`（字段级覆盖 result，L324-337 + types.ts L76-100 合并语义）、`declareToolChanges`（每次请求前把 transcript 声明的工具集与可执行工具集的差量写成 system message 的 toolsAdded/Removed，agent-loop.ts L322-374）。

## 4. Tool Runtime

**统一接口**【source】

## 5. Human-in-the-loop（审批）

**结论：Pi 核心没有内置权限/审批系统，是设计立场而非缺失。**
- 【source】根 `README.md` "Permissions & Containerization" 一节：*"Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it."* 并指向 `packages/coding-agent/docs/containerization.md` 的三种容器化模式（Gondolin 扩展 / Docker / OpenShell）。
- 【source】【docs】替代机制是 **extension `tool_call` 钩子可 block**：`ToolCallEventResult{block?, reason?, terminate?}`（extensions/types.ts L1217-1228）；runner 短路返回（runner.ts L1137-1156）；文档 *"tool_call can mutate input or block execution"*（docs/extensions.md L103）。官方示例 `packages/coding-agent/examples/extensions/permission-gate.ts`：对 `rm -rf`/`sudo`/`chmod 777` 用 `ctx.ui.select` 弹确认，**无 UI（print/json 模式）时默认 block**（`ctx.hasUI` 分支）。
- **RPC 下的远程审批**：extension UI 请求被序列化为 stdout 的 `extension_ui_request{id, method: select|confirm|input|editor|notify|setStatus|setWidget|setTitle|set_editor_text, timeout?}`，客户端回 `extension_ui_response{id, value|confirmed|cancelled}`（rpc-types.ts L246-291）；`ExtensionContext.hasUI`（"true in TUI and RPC modes"，types.ts L318-319）。
- 其余用户交互面：`project_trust` 事件（项目信任，L525-547）、`user_bash`（`!` 命令拦截/接管，L1234-1244）、`ui.confirm/select/input`（L137-145，含 `AbortSignal` 可编程取消，L103）。

对 ARI 的启示：**审批不进 runtime 核心协议，而是作为 (a) 可 block 的工具前置钩子 + (b) 通用 UI 请求/响应通道**存在；runtime 只保证 "block 决策产生 isError 工具结果" 这一契约。

## 6. File / Diff

- **edit 工具产出结构化 diff**：`EditToolDetails{diff, patch, firstChangedLine}`（edit.ts L70-77）；execute 内 `generateDiffString` + `generateUnifiedPatch`（edit-diff.ts L365-376，unified patch context=4）写进 `details`（edit.ts L201-211）；TUI renderer `renderers/edit.ts` 渲染预览与结果 diff（L95-209，`renderDiff` 组件）。**LLM 只收到一句 "Successfully replaced N block(s)"，diff 是 details 侧信道**（edit.ts L206-211）。
- **写冲突防护**：per-path 互斥队列 `withFileMutationQueue`（edit.ts L165 调用；tools/file-mutation-queue.ts）；BOM/换行符/模糊匹配处理（edit-diff.ts L11-34, L207）。
- **文件追踪（聚合级）**：`extractFileOpsFromMessage`（compaction/utils.ts L29-52）从 read/write/edit 工具结果提取 read/written/edited 集合，`computeFileLists` 产出 `{readFiles, modifiedFiles}`（L62-66）写进 **CompactionEntry/BranchSummaryEntry.details**（compaction.ts L1079-1080）——用于摘要与恢复上下文，**不是**发给客户端的文件变更事件。
- **git**：核心无 git 集成；`examples/extensions/git-checkpoint.ts` 示例由扩展实现。【docs】containerization.md 提供沙箱边界。
- **给客户端的文件变更信号** = `tool_execution_start/update/end` 的 args/details + 渲染器；无独立 "file_changed" 事件类型（源码中未找到）。

## 7. Command / Terminal（bash）

- **执行**：`spawn` + `killProcessTree`（bash.ts L11-18）；`commandPrefix` 注入、`spawnHook`（改写 command/cwd/env，L213-217）、PI_* 会话环境变量（`bashToolSystemPromptContribution`，L41-44）。
- **流式输出**：`OutputAccumulator` 增量快照 → 节流 `onUpdate`（BASH_UPDATE_THROTTLE_MS，`renderers/bash.ts`）→ `tool_execution_update`；结束时一次最终快照（bash.ts L262-330）。
- **截断**：`DEFAULT_MAX_LINES=2000`、`DEFAULT_MAX_BYTES=50KB`（truncate.ts L11-12），截断时全量输出落 temp file，`details{truncation, fullOutputPath}` + 尾注 "[Showing lines X-Y of Z. Full output: path]"（bash.ts L320-336）。
- **超时**：模型可传 `timeout`（秒，无默认；上限 2^31-1 ms，L30-38）；超时 → kill tree → "Command timed out after N seconds"（L116-121, L367-369）。
- **退出码**：非 0 → throw → isError 结果，正文附输出与 "Command exited with code N"（L372-374）；信号杀死按 128+n 约定（`BashOperations.exec` 注释 L60-64）。**取消**：abort → killProcessTree → "Command aborted"（L364-366）。**detached 子进程**：`trackDetachedChildPid`（utils/shell.ts L198-202），进程退出时统一收割（rpc-mode.ts `killTrackedDetachedChildren`）。
- **后台执行**：bash 工具本身**不支持后台化**（源码中未找到 run_in_background 类参数）。
- **用户直跑 `!` 命令**：`BashResult{output, exitCode, cancelled, truncated, fullOutputPath?}`（bash-executor.ts L29-39）→ `BashExecutionMessage`（可 `!!` 排除出上下文，messages.ts L37-40）；RPC 有专属 `bash` 命令与 `bash_execution_update` 流（rpc-types.ts L55-56；docs/json.md RPC-only events 节）。

## 11. Streaming 细节

**packages/ai 事件粒度**【source】：`AssistantMessageEvent`（ai/types.ts L652-668）：`start` / `text_start|text_delta{text_delta 带 delta}|text_end{content}` / `thinking_start|thinking_delta|thinking_end` / `toolcall_start|toolcall_delta|toolcall_end{toolCall}` / `done{reason, message}` / `error{reason, error}`；每个事件带 `contentIndex` 与 `partial`（**共享的 live 快照引用**而非事件时快照，L644-651 注释）。红线契约（L638-650）：`start` 必须先行、`done/error` 终结、redacted thinking 可无 delta。

**agent 层转发**【source】：`streamAssistantResponse`（agent-loop.ts L380-466）把 provider 事件转成 `message_start` → 每个 delta 一个 `message_update{assistantMessageEvent, message}` → `message_end`；partial 消息实时入 context 数组（L415-416），`done` 后以最终消息替换。**`start/done/error` 不作为 message_update 出现在线上**（docs/json.md "The normal agent loop translates provider-level start/done/error into message_start/message_end"）。

**wire 优化**【source】：`toJsonEvent`（`modes/json-event.ts:40-61`）剥离 `partial` 快照（保持流体积线性），`toolcall_start` 附 `id/toolName`；`message_update` 顶层带累计 `usage`。RPC/JSON 事件序列示例见 docs/json.md Event sequence 节（`agent_start → turn_start → message_start(user) → message_end → message_start(assistant, stopReason:"pending") → message_update(text_delta) → message_end → turn_end → agent_end{willRetry} → agent_settled`）。

**工具流**：`tool_execution_update{partialResult}`（bash 节流、自定义工具自由）。**RPC `agent_settled`**（agent-session.ts L171）= "不会再自动续跑（retry/overflow 恢复/队列）"，比 `agent_end` 晚 —— ARI 需要 equivalent 语义。

## 14. Shell 必须看到 vs Runtime 内部（ARI 设计结论）

**Shell（front-end）必须看到的（协议面）**：
1. **消息与事件流**：`AgentEvent` 10 事件 + 会话级扩展（agent_settled、queue_update、compaction_*、retry_*、entry_appended、session_info_changed）。Pi 证明 10 个低层事件足以驱动任意 UI；产品语义（settled/queue/retry）适合作为上层可选事件。
2. **流式增量**：`{type, contentIndex, delta}` 粒度 + 显式 `*_end` 权威内容 + `message_end` 最终消息；**线上不传 partial 快照**（体积线性），`toolcall_start` 附 id/toolName。usage 随 message_update 携带。
3. **工具执行的 UI 契约**：`toolCallId` 关联 start/update/end；`result.details` 作为"给渲染器的结构化自由字段"（diff、truncation、fullOutputPath），`result.content` 才是给模型的 —— **模型可见与 UI 可见双通道分离**是 Pi 最值得抄的决策。
4. **状态快照**：get_state 的一次性可观测状态（isStreaming/isCompacting/队列模式/模型/thinking）。
5. **控制动词**：prompt/steer/follow_up/abort/clear_queue/set_model/set_thinking_level/compact/fork/switch_session/get_tree/get_entries。
6. **审批通道**：通用 UI request/response（select/confirm/input + timeout + cancelled），配合可 block 的工具前置钩子；无 UI 环境默认 block 的安全缺省。
7. **会话树**：entry id/parentId/leaf + get_tree；branch=移动 leaf，fork=复制路径到新文件（parentSession 链）。

**Runtime 内部（不该进协议）**：
1. **provider 适配**（StreamFn、api/provider 兼容层、OAuth、retry/backoff、cache warmer）——Agent 核心连 provider 目录都不 import。
2. **prompt/tools 的组装**：以 transcript 内 system message 增量（sections/toolsAdded/Removed）表达，协议只需"回放语义"，不需 prompt builder。
3. **convertToLlm/transformContext**、自定义消息→user 的映射、上下文估算。
4. **compaction 算法本身**：协议只需 CompactionEntry 的 checkpoint/firstKeptEntryId 语义与三个触发原因。
5. **工具执行调度**（parallel/sequential、terminate 批量规则、mutation queue、进程树管理）——协议只暴露事件顺序契约（end 按完成序、result 消息按源序）。
6. **重试策略与 loop 策略**（Pi 无 max iterations/loop detection —— ARI 若要加，应为显式配置而非隐式行为）。

**ARI 借鉴要点（按优先级）**：
- 事件最小集 = Pi 的 10 事件 + `agent_settled`；`willRetry` 类语义字段直接放 agent_end。
- `AgentMessage = 标准消息 + 可注册扩展 role` + `convertToLlm` 边界 —— 让 shell/扩展消息不污染模型上下文。
- system-message 承载 prompt/tool loadout 增量（可回放、可 diff、天然持久化）。
- 会话 = append-only JSONL 树（id/parentId/leaf），branch 免费获得；fork=新文件+parentSession 指针；损坏行跳过即崩溃恢复。
- stopReason==="length" 时全部 tool call 判失败并要求重发（安全缺省）。
- 工具结果 `content(details)` 双通道 + renderer 注册表。
- 审批 = block-hook + UI 请求通道，runtime 无内置策略。
- RPC 传输经验：严格 LF 分帧、stdout 背压、关 stdin 关停、id 关联、prompt 成功≠run 完成（要等 settled）。
