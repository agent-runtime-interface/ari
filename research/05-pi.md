> Survey subject: `@earendil-works/pi-mono` (Mario Zechner / badlogic, pi.dev). Local clone (not committed to this repo; the path varies by machine).

## 0. Overall architecture: three-layer separation

Pi's layering is the most direct prior for ARI:

1. **`packages/ai` (model API layer)**: a unified multi-provider streaming LLM API and message types (`AssistantMessage`, `ToolCall`, thinking block, `AssistantMessageEvent`). It knows nothing about "agents".
2. **`packages/agent` (agent runtime layer)**: the `Agent` class + the low-level `agentLoop` + an event stream (`AgentEvent`). Model calls are injected via `StreamFn` (the `StreamFn` type at `packages/agent/src/types.ts:33-37`, whose comment states explicitly "The loop passes a normalized transcript ... never by `context.systemPrompt`"), making it provider-agnostic; `packages/agent/src/stream-fn.ts:1-20` provides the `setDefaultStreamFn` fallback injection (`packages/coding-agent/src/core/sdk.ts:45` calls `setDefaultStreamFn(streamSimple)`).
3. **`packages/coding-agent` (product layer)**: CLI, TUI, session persistence, built-in tools, extensions, RPC/print/json modes, compaction, retry.

One important "in progress" fact: `packages/agent/src/harness/` (`agent-harness.ts`, `runtime/`, `session/`, `pico3/`) is a **durable runtime** (AgentHarness) with `packages/agent/docs/harness.md` as its normative document; §0.9 (from around L141 onward) declares WP00–WP07 implemented and the rest (e.g. `watchSession` R12, schema migration R11, C1 remote transport) not implemented. The body of this survey follows the shipping `Agent` + `AgentSession` as the main line, with the durable harness listed separately as an evolution direction.

## 1. Session: creation, resume, IDs, persistence, multiple clients, interruption, fork, crash recovery

**Creation and IDs** [source]
- `SessionManager.newSession()` (`packages/coding-agent/src/core/session-manager.ts:1057-1083`): generates `sessionId = createSessionId()` (`uuidv7()`, L264-266), and writes `SessionHeader{type:"session", version:CURRENT_SESSION_VERSION(=3), id, timestamp, cwd, parentSession?}` (L43-50, L1063-1070). File name `<ISO timestamp with : and . replaced by ->_<sessionId>.jsonl` (L1078-1081).
- A custom `--session-id` must pass the `assertValidSessionId` regex (L268-274). Entry ids are 8 hex characters (`generateId`, L277-284).

**Persistence format and location** [source][docs]
- JSONL, an append-only tree structure: every entry is a `SessionEntryBase{type, id, parentId: string|null, timestamp}` (L57-62). `FileEntry = SessionHeader | SessionEntry` (L197). **[docs]** `packages/coding-agent/docs/session-format.md` (around L1-10): `~/.pi/agent/sessions/--<path>--/<timestamp>_<session-id>.jsonl`; v1 linear → v2 tree → v3 renames hookMessage to custom, with automatic migration on load (`migrateToCurrentVersion`, session-manager.ts L1092).
- The directory is encoded from the cwd: `getDefaultSessionDirPath` strips the cwd's leading `/`, replaces `/\:` with `-`, and wraps the result in `--...--` (L589-592); the agent dir is `~/.pi/agent` (`packages/coding-agent/src/config.ts:528-531`, overridable via the `PI_CODING_AGENT_DIR` env var, L508). Sessions dir: `config.ts:572-574`.
- Deferred-persistence contract: **no file is written before the first assistant message appears** (`_persist`, L1160-1187: writes are held while `hasAssistant` is false and nothing has been flushed; the first flush creates the file exclusively with `openSync(..., "wx")` and writes everything in full, after which entries are appended one by one with `appendFileSync`). Tolerance for empty files / corrupted lines: `loadEntriesFromFile` skips lines that fail `JSON.parse` (L616-624), and a `\n` is appended to the end of the file (L668).
- **No separate "leaf pointer file"**: the leaf is simply "the last entry in the file" (`_buildIndex`: iterates fileEntries, `this.leafId = entry.id`, L1103-1122). The `parentId` of any entry in the tree is the source of truth for branching.

**Resume** [source]
- CLI flags: `--continue|-c` (continue the most recent session), `--resume|-r` (picker), `--session <path|id>`, `--session-id`, `--fork <id>`, `--session-dir` (`packages/coding-agent/src/cli/args.ts:20-30,110-141,293-297`).
- `findMostRecentSession(sessionDir, cwd)`: sorts the .jsonl files by mtime, reads the first-line header, and checks that `cwd` matches (L749-768; `readSessionHeader` has a 1MB scan cap, L607 and L685-727).

**Interruption (ESC abort)** [source]
- Interactive mode: `defaultEditor.onEscape` (`packages/coding-agent/src/modes/interactive/interactive-mode.ts:2965-2996`): while isStreaming, `restoreQueuedMessagesToEditor({ abort: true })` — **abort also returns the queued steering/follow-up messages to the editor**; while isBashRunning, `abortBash()`; double-ESC on an empty editor (<500ms, L2979) opens `/tree` or the user-message picker depending on settings (branch navigation). Keybinding registration: `app.interrupt: "escape"` (`packages/coding-agent/src/core/keybindings.ts:93`).
- Runtime side: `AgentSession.abort()` (`packages/coding-agent/src/core/agent-session.ts:2075-2082`) = abort retry + compaction + branch summary + `agent.abort()` (`AbortController.abort()`, `packages/agent/src/agent.ts:338-340`) + `waitForIdle()`. On the RPC side this corresponds to the `abort` command (rpc-types.ts L25).

**Fork / branch (session tree)** [source]
- **Branch** (same file): `branch(branchFromId)` only moves the leaf pointer (L1572-1577); subsequent appends create a new child chain; `resetLeaf()` (L1584-1586) allows re-editing the first user message (new root); `branchWithSummary(fromId, summary, ...)` appends a `BranchSummaryEntry{fromId, summary, usage?, fromHook?}` recording the abandoned path (L1593-1618; type at L106-116).
- **Fork** (new file): `createBranchedSession(leafId)` copies the root→leaf path into a new session file, with the header carrying `parentSession: <old file path>` (L1625-1724). CLI `--fork`, RPC `fork`/`clone` commands, and extension `ctx.fork()` (extensions/types.ts L373-377). `navigateTree(targetId, {summarize,...})` can generate an LLM summary when switching tree nodes (agent-session.ts L3581).
- [docs] The Tree Structure section of `docs/session-format.md` gives a tree diagram and the definition "the leaf is the current position".

**Crash recovery** [source]
- Three mechanisms: (1) append-only + skipping corrupted lines (L616-624); (2) no file is created before the first assistant message, avoiding empty / half-initialized files; (3) crashes are recorded in `crashes.json` (`packages/coding-agent/src/core/crash-log.ts:19-32`, `{timestamp, version, kind: "uncaught_exception"|"fatal_error", message, stack, sessionFile, cwd}`, at most 5 entries kept for 7 days). The durable harness (harness/docs) instead does explicit operation-level recovery (an effect_pending state machine), but per §0.9 part of it is not yet in the product.

**Multiple clients** [source]
- The shipping RPC mode is a **single stdin/stdout, single-client** subprocess model (`docs/rpc.md`: "Pi as a long-lived subprocess controlled through JSON records on stdin and stdout").
- The experimental stack supports multiple clients: `packages/server/src/session-router.ts:32-42` (`HostedSession{id, handle, attachments: Set<ClientAttachment>}`, one session with multiple attachments/clients), and the protocol layer `packages/protocol/README.md` (PROTOCOL_VERSION 8, `{serverId, sessionId, attachmentId}` routing, attach/detach). Also `packages/coding-agent/src/experimental/session-worker-manager.ts` (a session worker process pool + chord services).

## 2. Message model: a three-tier type system (core prior for ARI)

### 2.1 Model API messages (packages/ai)

`Message = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage` (`packages/ai/src/types.ts:553`).

- `SystemMessage` (L491-507): `content` + **`sections?: Record<string, string|null>`** (named prompt sections; null deletes) + **`toolsAdded?: Tool[]` / `toolsRemoved?: ToolReference[]`**. Comment: **the system messages in the transcript carry the prompt and the tool declarations; replaying all system messages yields the current prompt/tools** — an incremental, replayable loadout protocol (something ARI should absorb as a priority).
- `UserMessage` (L509-513): `content: string | (TextContent|ImageContent)[]` + timestamp.
- `AssistantMessage` (L515-537): `content: (TextContent | ThinkingContent | ToolCall)[]`; `api/provider/model/responseModel?/responseId?`; `providerThinkingLevel?`; `diagnostics?`; `usage: Usage`; `stopReason: StopReason`; `deferred?: DeferredHandle` (a polling handle for deferred responses, L469-479); `errorMessage?/rawStopReason?/endTurn?`.
- `ToolResultMessage` (L539-551): `toolCallId, toolName, content: (TextContent|ImageContent)[], details?, usage?, isError, timestamp`.
- Content blocks: `TextContent{type:"text", text, textSignature?}` (L364-368); `ThinkingContent{type:"thinking", thinking, thinkingSignature?, redacted?}` (L370-378; the encrypted payload of redacted thinking is stored in the signature to be sent back); `ImageContent{type:"image", data(base64), mimeType}` (L380-384); `ToolCall{type:"toolCall", id, name, arguments: JsonObject, thoughtSignature?, namespace?}` (L386-394).
- `StopReason = "pending"|"stop"|"length"|"toolUse"|"error"|"aborted"|"deferred"` (L419). `Usage` (L396-417): input/output/cacheRead/cacheWrite/cacheWrite1h?/**reasoning?**/totalTokens/cost{...}.
- `Tool` (L600-605): `{name, description, parameters(TypeBox TSchema), constrainedSampling?}`.

### 2.2 AgentMessage (runtime messages, extensible)

`AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]` (`packages/agent/src/types.ts:370`), extended via declaration merging (comment at L361-363). coding-agent registers 4 kinds (`packages/coding-agent/src/core/messages.ts:71-76`): `bashExecution` (L29-40: command/output/exitCode/cancelled/truncated/fullOutputPath/excludeFromContext), `custom` (L47-54: customType/content/display/details), `branchSummary` (L57-61), `compactionSummary` (L66-70). `convertToLlm()` (L149-185) maps them into user messages (or drops them per `excludeFromContext`); the `Agent` default `defaultConvertToLlm` lets only the four standard roles through (`packages/agent/src/agent.ts:38-46`).

### 2.3 Runtime events (packages/agent `AgentEvent`) — prior for the ARI event vocabulary

`packages/agent/src/types.ts:485-500`, **10 kinds in total**:
- Lifecycle: `agent_start`, `agent_end{messages}`;
- Turn: `turn_start`, `turn_end{message, toolResults}` (comment: one turn = one assistant response + its tool calls/results);
- Message: `message_start{message}`, `message_update{message, assistantMessageEvent}` (only during assistant streaming), `message_end{message}`;
- Tool: `tool_execution_start{toolCallId, toolName, args}`, `tool_execution_update{..., partialResult}`, `tool_execution_end{..., result, isError}`.

### 2.4 Session-level events (coding-agent `AgentSessionEvent`)

`packages/coding-agent/src/core/agent-session.ts:164-205`: the full `AgentEvent` set (with `willRetry` added to `agent_end`) + `agent_settled` ("Pi will no longer continue running on its own") + `queue_update{steering, followUp}` + `compaction_start/end{reason: manual|threshold|overflow}` + `entry_appended{entry}` + `session_info_changed{name}` + `thinking_level_changed{level}` + `auto_retry_start/end` + `summarization_retry_*` + `bash_execution_update{id?, delta}` (RPC user bash output).

### 2.5 Session persistence entries (11 kinds + header)

`session-manager.ts:183-194`: `SessionMessageEntry`, `ThinkingLevelChangeEntry`, `ModelChangeEntry`, `UsageEntry` (kind/provider/model/usage/note, L80-89), `CompactionEntry` (summary/firstKeptEntryId/tokensBefore/details/usage/fromHook/**a complete systemMessage checkpoint**, L91-104), `BranchSummaryEntry` (L106-116), `CustomEntry` (kept out of the LLM context), `CustomMessageEntry` (**does** enter the LLM context; display drives the TUI, L159-165), `ContextEditEntry` (append-only rewriting of an earlier entry's model-visible content, or nulling it out to omit it, L175-180), `LabelEntry`, `SessionInfoEntry`.

## 3. Agent Loop

**Entry point and structure** [source]
- `agentLoop(prompts, context, config, signal, streamFn)` / `agentLoopContinue(...)` (`packages/agent/src/agent-loop.ts:37-99`) returns an `EventStream<AgentEvent, AgentMessage[]>`; `runLoop` (L162-320) is a double loop:
  - **Inner**: `while (hasMoreToolCalls || pendingMessages.length > 0)`: in order, `prepareNextTurn` (may swap context/model/thinkingLevel, L184-207) → append prepared/steering messages → `prepareRequest` (L218-238) → `streamAssistantResponse` → if `stopReason` is error/aborted, wrap up immediately (L244-255) → collect toolCall blocks → execute tools → `finishTurn` (may return `{action:"continue"|"end"}`) → `turn_end`.
  - **Outer**: when the agent would otherwise stop, pull `getFollowUpMessages()` (L301-307); if any exist, keep running. Otherwise, if `finishTurn` supplied an `explicitContinuation`, run one extra context-only request (L309-313); otherwise exit and emit `agent_end`.
- **Handling of stopReason==="length"**: every tool call in a token-truncated assistant message is unconditionally marked failed (`failToolCallsFromTruncatedMessage`, L475-500; the error text explicitly asks the model to re-issue them), preventing execution of calls whose arguments were silently truncated. A detail comment (L468-474) notes that streamed arguments are completed via a "JSON salvage parser" and may parse successfully yet be semantically incomplete — a lesson of direct value to ARI.

**Steering / followUp (queued injection)** [source]
- `Agent.steer(message)` / `followUp(message)` (`packages/agent/src/agent.ts:296-303`); two `PendingMessageQueue`s, `QueueMode = "all" | "one-at-a-time"` (types.ts L55), default `one-at-a-time` (agent.ts L244-245); `steeringMode`/`followUpMode` setters (L278-293). Semantics: steering is injected after tool execution of the current assistant turn finishes and before the next request ("Tool calls from the current assistant message are not skipped", types.ts L279-289); followUp is injected when the agent would otherwise stop (L291-302). While `prepareNextTurn` takes long (e.g. compaction), steering is polled again (agent-loop.ts L200-205), but in one-at-a-time mode the extra pull happens only on an empty first-round poll, to avoid injecting two messages at once (comment at L203-205).
- RPC side: the `prompt` command carries `streamingBehavior: "steer"|"followUp"`, and there are separate `steer`/`follow_up`/`clear_queue` commands (rpc-types.ts L22-26, L43-44).

**Parallel tool execution** [source]
- `ToolExecutionMode = "sequential" | "parallel"` (types.ts L47); `AgentLoopConfig.toolExecution` defaults to **parallel** (agent.ts L250); **per-tool override**: `AgentTool.executionMode` (types.ts L461-467) — if even one tool in the batch is sequential, the whole batch executes sequentially (agent-loop.ts L512-519).
- Parallel implementation (L583-657): preparation/validation/beforeToolCall run sequentially, execution is concurrent; `tool_execution_end` is emitted in **completion order**, while the tool-result messages are emitted in **assistant source order** (the comment at types.ts L39-46 states this ordering contract explicitly). **Batch termination rule**: early termination only if all results have terminate===true (`shouldTerminateToolBatch`, L685-687).

**Abort** [source]
- One `AbortController` per run (`ActiveRun`, agent.ts L175-179 and L503-526); `agent.abort()` aborts it. In sequential execution, `signal?.aborted` is checked after each tool call to break out (agent-loop.ts L572-574); in the parallel case, calls that have not started return an aborted error result directly (L617-625). Tools are responsible for honoring the signal themselves (e.g. bash `killProcessTree`, see §7). After an abort, the loop winds down with stopReason "aborted" (L244-255).

**Failure / retry** [source]
- A tool execution that throws → `createErrorToolResult` (L863-868) → a toolResult message with `isError: true` (L880-893); **no tool-level auto-retry**. Retrying assistant errors lives at the product layer: `AgentSession._prepareRetry` (agent-session.ts L3380-3406; defaults maxRetries=3 and baseDelayMs=2000 with exponential backoff, settings-manager.ts L932-937), with retryability decided by `isRetryableAssistantError`; **context overflow is not retryable and recovers via compaction** (L3324-3330). Events: `auto_retry_start/end`.
- **Max iterations / loop detection / budget caps: not found in the source** (grepping `maxTurns|maxIterations|loop detection` yields nothing). Loop termination relies entirely on the model stopping + the `finishTurn` hook + empty queues. [docs] extensions.md "Guard continuation conditions because an unconditional continuation can loop" also confirms there is no hard guardrail.

**Other hooks**: `transformContext` (context window management, types.ts L221-240); `getApiKey` (refreshes the OAuth token during long runs, L242-250); `beforeToolCall` (can block/terminate, L315-322); `afterToolCall` (field-level result override, L324-337 + merge semantics in types.ts L76-100); `declareToolChanges` (before each request, the delta between the tool set declared in the transcript and the executable tool set is written into the system message as toolsAdded/Removed, agent-loop.ts L322-374).

## 4. Tool Runtime

**Unified interface** [source]
- Runtime layer `AgentTool` (`packages/agent/src/types.ts:443-468`): `name/label/description/parameters(TypeBox)/constrainedSampling?/prepareArguments?/execute(toolCallId, params, signal?, onUpdate?)/replay?: "never"|"safe"/executionMode?`. `onUpdate: AgentToolUpdateCallback` (L440) is for streaming partial results.
- Product layer `ToolDefinition` (`packages/coding-agent/src/core/extensions/types.ts:455-504`) adds on top of AgentTool: `promptSnippet?/promptGuidelines?` (into the system prompt), `renderShell?: "default"|"self"`, **`renderCall?/renderResult?`** (TUI renderers; their parameters include `ToolRenderContext{args, toolCallId, state, isPartial, isError, expanded...}` L425-450 and `ToolRenderResultOptions{expanded, isPartial}` L417-422). `wrapToolDefinition` (`packages/coding-agent/src/core/tools/tool-definition-wrapper.ts:9-24`) downgrades a definition into an AgentTool to plug it into the core loop.
- **Tool call ID**: produced by the model (`ToolCall.id`); the first parameter of `execute()` is the toolCallId, and the toolResult is correlated by the same id (agent-loop.ts L880-893).
- **Result type**: `AgentToolResult{content: (Text|Image)[], details: T, usage?, terminate?}` (types.ts L420-432); `details` is the **structured channel for the UI** (bash truncation/fullOutputPath, edit diff/patch), while `content` is for the model. `usage` is the tool's own consumption and is not counted in the main context accounting (comment at L426).

**Built-in tools** [source]
- `ToolName = "read"|"bash"|"powershell"|"edit"|"write"|"grep"|"find"|"ls"` (`packages/coding-agent/src/core/tools/index.ts:95`); read/bash/edit/write are active by default (the selectedTools default at `system-prompt.ts:57`; the `agent-session.ts:235` comment "Initial active tool names. Default: [read, bash, edit, write]"). `createCodingTools/createReadOnlyTools` (tools/index.ts L195/L204).
- The loadout is mutable at runtime: `AgentSession.getActiveToolNames()/setActiveToolsByName()` (agent-session.ts L1252/L1279); changes are announced incrementally via a system message (§3 declareToolChanges).

**Streaming / cancellation / progress**: bash emits a throttled `onUpdate` every `BASH_UPDATE_THROTTLE_MS` (bash.ts L262-286); the events are converted into `tool_execution_update` (agent-loop.ts L786-800). Cancellation relies on AbortSignal + the tool's own diligence.

**What the shell should see vs internals**: see §14.

## 5. Human-in-the-loop (approval)

**Conclusion: Pi's core has no built-in permission/approval system — this is a design stance, not an omission.**
- [source] The "Permissions & Containerization" section of the root `README.md`: *"Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it."* It points to the three containerization modes in `packages/coding-agent/docs/containerization.md` (Gondolin extension / Docker / OpenShell).
- [source][docs] The substitute mechanism is the **extension `tool_call` hook, which can block**: `ToolCallEventResult{block?, reason?, terminate?}` (extensions/types.ts L1217-1228); the runner short-circuits and returns (runner.ts L1137-1156); docs *"tool_call can mutate input or block execution"* (docs/extensions.md L103). The official example `packages/coding-agent/examples/extensions/permission-gate.ts`: for `rm -rf`/`sudo`/`chmod 777` it pops a confirmation via `ctx.ui.select`, and **blocks by default when there is no UI (print/json modes)** (the `ctx.hasUI` branch).
- **Remote approval over RPC**: extension UI requests are serialized to stdout as `extension_ui_request{id, method: select|confirm|input|editor|notify|setStatus|setWidget|setTitle|set_editor_text, timeout?}`, and the client replies `extension_ui_response{id, value|confirmed|cancelled}` (rpc-types.ts L246-291); `ExtensionContext.hasUI` ("true in TUI and RPC modes", types.ts L318-319).
- The remaining user-interaction surfaces: the `project_trust` event (project trust, L525-547), `user_bash` (interception/takeover of `!` commands, L1234-1244), `ui.confirm/select/input` (L137-145, with an `AbortSignal` for programmatic cancellation, L103).

Implication for ARI: **approval stays out of the runtime core protocol and exists as (a) a tool pre-call hook that can block + (b) a generic UI request/response channel**; the runtime only guarantees the contract that "a block decision produces an isError tool result".

## 6. File / Diff

- **The edit tool produces a structured diff**: `EditToolDetails{diff, patch, firstChangedLine}` (edit.ts L70-77); inside execute, `generateDiffString` + `generateUnifiedPatch` (edit-diff.ts L365-376, unified patch with context=4) are written into `details` (edit.ts L201-211); the TUI renderer `renderers/edit.ts` renders preview and result diffs (L95-209, the `renderDiff` component). **The LLM receives only the sentence "Successfully replaced N block(s)"; the diff is a details side channel** (edit.ts L206-211).
- **Write-conflict protection**: a per-path mutual-exclusion queue, `withFileMutationQueue` (called at edit.ts L165; tools/file-mutation-queue.ts); handling of BOMs / line endings / fuzzy matching (edit-diff.ts L11-34, L207).
- **File tracking (aggregation level)**: `extractFileOpsFromMessage` (compaction/utils.ts L29-52) extracts read/written/edited sets from read/write/edit tool results, and `computeFileLists` produces `{readFiles, modifiedFiles}` (L62-66), written into **CompactionEntry/BranchSummaryEntry.details** (compaction.ts L1079-1080) — used for summaries and for restoring context, **not** a file-change event sent to the client.
- **git**: no git integration in the core; the `examples/extensions/git-checkpoint.ts` example implements it via an extension. [docs] containerization.md provides sandbox boundaries.
- **File-change signals to the client** = the args/details of `tool_execution_start/update/end` + renderers; there is no separate "file_changed" event type (not found in the source).

## 7. Command / Terminal (bash)

- **Execution**: `spawn` + `killProcessTree` (bash.ts L11-18); `commandPrefix` injection, `spawnHook` (rewrites command/cwd/env, L213-217), and PI_* session environment variables (`bashToolSystemPromptContribution`, L41-44).
- **Streaming output**: `OutputAccumulator` incremental snapshots → throttled `onUpdate` (BASH_UPDATE_THROTTLE_MS, `renderers/bash.ts`) → `tool_execution_update`; one final snapshot at the end (bash.ts L262-330).
- **Truncation**: `DEFAULT_MAX_LINES=2000`, `DEFAULT_MAX_BYTES=50KB` (truncate.ts L11-12); on truncation the full output goes to a temp file, with `details{truncation, fullOutputPath}` + the trailing note "[Showing lines X-Y of Z. Full output: path]" (bash.ts L320-336).
- **Timeout**: the model may pass `timeout` (seconds, no default; capped at 2^31-1 ms, L30-38); on timeout → kill tree → "Command timed out after N seconds" (L116-121, L367-369).
- **Exit codes**: non-zero → throw → an isError result, with the output and "Command exited with code N" appended to the body (L372-374); kills by signal follow the 128+n convention (`BashOperations.exec` comment, L60-64). **Cancellation**: abort → killProcessTree → "Command aborted" (L364-366). **Detached child processes**: `trackDetachedChildPid` (utils/shell.ts L198-202), reaped uniformly when the process exits (rpc-mode.ts `killTrackedDetachedChildren`).
- **Background execution**: the bash tool itself **does not support backgrounding** (no run_in_background-like parameter found in the source).
- **User-run `!` commands**: `BashResult{output, exitCode, cancelled, truncated, fullOutputPath?}` (bash-executor.ts L29-39) → `BashExecutionMessage` (can be excluded from context with `!!`, messages.ts L37-40); RPC has a dedicated `bash` command and a `bash_execution_update` stream (rpc-types.ts L55-56; the RPC-only events section of docs/json.md).
- Windows: a separate powershell tool (tools/powershell.ts).

## 8. Context management

- **System prompt = the system messages in the transcript**: the first is the complete prompt (sections + tool declarations), and subsequent ones are incremental patches (section replacement/deletion + toolsAdded/Removed) (ai/types.ts L481-507). The coding-agent-side section set is in `system-prompt.ts` (ordered tags such as preamble/tools/project_context/skills/cwd, L60-72 and L164).
- **Context files**: `loadProjectContextFiles` (resource-loader.ts L122-160) searches from `~/.pi/agent` (global) plus the cwd up to the root directory, level by level, for `AGENTS.override.md > AGENTS.md > CLAUDE.md` (L72), with worktree shadow deduplication (L88-118); rendered as `<project_instructions path="...">` (system-prompt.ts L72-77). **Skills** are loaded on demand (docs/how-pi-works.md "Full skill instructions are loaded on demand").
- **Compaction** (`core/compaction/compaction.ts`):
  - Three triggers: `manual` (/compact), `threshold` (`shouldCompact: contextTokens > contextWindow - reserveTokens`, L289-292; defaults `reserveTokens=16384, keepRecentTokens=20000`, L144-151), `overflow` (compact and retry after a request overflows; event `compaction_end.willRetry=true`, docs/json.md).
  - Before a new prompt, the previous assistant usage is checked (`_checkCompaction(lastAssistant, false)` inside prompt in agent-session.ts, around L1695-1697).
  - Artifact: `CompactionEntry{summary, firstKeptEntryId, tokensBefore, full systemMessage checkpoint, usage, details{readFiles, modifiedFiles}}`; when rebuilding context, the summary replaces the history before firstKeptEntryId (the Context Building section of session-format.md; `buildContextEntries`/`buildSessionProjection`/`buildSessionContext`, session-manager.ts L1483-1498).
  - Extensions can take over: `session_before_compact` can cancel/customize (extensions/types.ts L597-608); `CompactionEntry.fromHook` marks the origin.
- **Branch summary**: when switching tree nodes, an LLM summary is generated for the abandoned branch (`branchWithSummary`; `branch-summarization.ts`).
- **Append-only context rewriting**: `ContextEditEntry` (omits or replaces an entry's model-visible content; branch-relative; session-manager.ts L1358-1396 + session-format.md).
- **Token budget**: no hard budget truncator; `estimateTokens` is only a fallback estimate for compaction (compaction.ts L273-281). Tool output truncation is per-tool (§7). **Prompt cache**: `CacheWarmer` keeps it warm while idle (agent-session.ts L233-234), and usage entries record `cache_warm` consumption (session-manager.ts L1242-1256).

## 10. Subagents

- **No built-in subagent/task tool in the product** (not found in the source; `grep -r subagent packages/{agent,coding-agent}/src` only hits experimental code).
- Official example extension `packages/coding-agent/examples/extensions/subagent/`: **spawns a separate `pi` process (--mode json) per subagent**, isolating context; supports three modes — single / parallel (multiple tasks streaming simultaneously) / chain (the previous output is injected into the next as `{previous}`); agents are defined as `agents/*.md` (frontmatter: name/description/tools/model/systemPrompt, agents.ts L16-25); the README lists abort propagation (Ctrl+C kills the child processes) and usage accounting. I.e. **subagent = a user-level multi-process solution, not a runtime concept**.
- Experimental durable Task (pico3 kernel): `Task{id, conversationId, kind, input, status: pending|running|terminal, checkpoint?, abort?, outcome, after, owns: "conversations this task created", background?: "does not hold the conversation busy; survives conversation abort"}` (`packages/agent/src/harness/pico3/types.ts:126-138`); `taskApi` provides `task()/getTask()/waitForTask()` (kinds/task-api.ts). This is the prior for "a task owning its own session".
- **Lanes** (new harness): one session with multiple `AgentLane`s (each lane has an independent model config / queue / at most one operation; `main` is just an ordinary name; harness.md §0.2; `HarnessEvent` carries a `lane` field and there is a `lane_created` event, agent-harness.ts L372 and L388-397). Multi-agent parallelism = multiple lanes.
- Multi-session multi-process orchestration: `experimental/session-worker-manager.ts` + `experimental/coordinator.ts` (a unix socket control channel, peer message routing).

## 11. Streaming details

**packages/ai event granularity** [source]: `AssistantMessageEvent` (ai/types.ts L652-668): `start` / `text_start|text_delta{text_delta carries delta}|text_end{content}` / `thinking_start|thinking_delta|thinking_end` / `toolcall_start|toolcall_delta|toolcall_end{toolCall}` / `done{reason, message}` / `error{reason, error}`; every event carries `contentIndex` and `partial` (**a shared live snapshot reference**, not a snapshot taken at event time; comment at L644-651). Hard invariants (L638-650): `start` must come first, `done/error` are terminal, and redacted thinking may have no delta.

**agent-layer forwarding** [source]: `streamAssistantResponse` (agent-loop.ts L380-466) converts provider events into `message_start` → one `message_update{assistantMessageEvent, message}` per delta → `message_end`; the partial message enters the context array in real time (L415-416) and is replaced by the final message after `done`. **`start/done/error` do not appear on the wire as message_update** (docs/json.md "The normal agent loop translates provider-level start/done/error into message_start/message_end").

**Wire optimizations** [source]: `toJsonEvent` (`modes/json-event.ts:40-61`) strips the `partial` snapshot (keeping the stream volume linear) and attaches `id/toolName` to `toolcall_start`; `message_update` carries cumulative `usage` at the top level. For an RPC/JSON event sequence example, see the Event sequence section of docs/json.md (`agent_start → turn_start → message_start(user) → message_end → message_start(assistant, stopReason:"pending") → message_update(text_delta) → message_end → turn_end → agent_end{willRetry} → agent_settled`).

**Tool streaming**: `tool_execution_update{partialResult}` (throttled for bash, free-form for custom tools). **RPC `agent_settled`** (agent-session.ts L171) = "no further automatic continuation will happen (retry/overflow recovery/queues)"; it comes later than `agent_end` — ARI needs the equivalent semantics.

## 14. What the shell must see vs runtime internals (ARI design conclusions)

**What the shell (front-end) must see (the protocol surface)**:
1. **Messages and the event stream**: the 10 `AgentEvent` events + session-level extensions (agent_settled, queue_update, compaction_*, retry_*, entry_appended, session_info_changed). Pi proves that 10 low-level events suffice to drive any UI; product semantics (settled/queue/retry) fit as optional events at a higher layer.
2. **Streaming increments**: `{type, contentIndex, delta}` granularity + explicit `*_end` authoritative content + `message_end` with the final message; **no partial snapshots on the wire** (volume stays linear), `toolcall_start` carries id/toolName. usage travels with message_update.
3. **The tool-execution UI contract**: `toolCallId` correlates start/update/end; `result.details` serves as "the structured free-form field for the renderer" (diff, truncation, fullOutputPath), while `result.content` is what the model gets — **separating the model-visible and UI-visible channels** is Pi's most worth-copying decision.
4. **State snapshot**: get_state's one-shot observable state (isStreaming/isCompacting/queue modes/model/thinking).
5. **Control verbs**: prompt/steer/follow_up/abort/clear_queue/set_model/set_thinking_level/compact/fork/switch_session/get_tree/get_entries.
6. **Approval channel**: generic UI request/response (select/confirm/input + timeout + cancelled) combined with a tool pre-call hook that can block; with the safe default of blocking when there is no UI.
7. **Session tree**: entry id/parentId/leaf + get_tree; branch = move the leaf, fork = copy the path to a new file (parentSession chain).

**Runtime internals (should not enter the protocol)**:
1. **Provider adaptation** (StreamFn, the api/provider compatibility layer, OAuth, retry/backoff, cache warmer) — the Agent core does not even import a provider directory.
2. **prompt/tools assembly**: expressed as incremental system messages in the transcript (sections/toolsAdded/Removed); the protocol only needs "replay semantics", not a prompt builder.
3. **convertToLlm/transformContext**, the custom-message→user mapping, and context estimation.
4. **The compaction algorithm itself**: the protocol only needs the CompactionEntry checkpoint/firstKeptEntryId semantics and the three trigger reasons.
5. **Tool execution scheduling** (parallel/sequential, the terminate batch rule, the mutation queue, process tree management) — the protocol only exposes the event-ordering contract (end in completion order, result messages in source order).
6. **Retry policy and loop policy** (Pi has no max iterations/loop detection — if ARI adds them, they should be explicit configuration, not implicit behavior).

**Key takeaways for ARI (by priority)**:
- Minimal event set = Pi's 10 events + `agent_settled`; `willRetry`-style semantic fields go directly on agent_end.
- `AgentMessage = standard messages + registrable extension roles` + the `convertToLlm` boundary — so shell/extension messages do not pollute the model context.
- System messages carry prompt/tool loadout increments (replayable, diffable, naturally persisted).
- Session = an append-only JSONL tree (id/parentId/leaf); branching comes for free; fork = new file + parentSession pointer; corrupted-line skipping doubles as crash recovery.
- On stopReason==="length", all tool calls are marked failed and the model is asked to re-issue them (safe default).
- The tool-result `content(details)` dual channel + a renderer registry.
- Approval = block hook + UI request channel; the runtime has no built-in policy.
- RPC transport lessons: strict LF framing, stdout backpressure, shutdown on stdin close, id correlation, prompt success ≠ run completion (wait for settled).
